# modules/ - officially supported modules outside the standard library

This directory is where Yooperlang's own non-std modules live: things that are
worth maintaining and shipping, but that do not belong in `std/`.

The distinction is what a user has to accept. `std/` ships with the compiler and
everyone gets it whether they asked or not, so it stays small and stays free of
anything that drags in a system dependency. A module here is opt-in: a user
copies it into their program's own `modules/` folder, and the cost is theirs to
accept. That makes this the right home for

- clients for a specific service or protocol (a Mongo client, a Redis client),
- bindings to a popular C library, **declaring** the library with
  `extern "C" from library "..."` without vendoring the C sources themselves, so
  the user installs the library through their own package manager,
- anything useful enough to maintain but too opinionated or too heavy to force
  on every program that imports `std/core`.

## Layout

Each subdirectory is one module, and is exactly what a user installs:

```text
modules/
  README.md
  mongo/               module mongo;
    MODULE             advisory version info
    client.yoop
    client.test.yoop   tests ship with the module
  bson/                mongo may depend on this, FLAT beside it
    MODULE
    bson.yoop
```

The repo root is itself a modules root, so these modules resolve for each other
and for anything else in the tree by the ordinary rule: `import * as m from
"modules/mongo"` walks up from the importing file to the nearest `modules`
directory. Modules here depend on each other **flat**, never by nesting - a
module carrying its own `modules/` directory is a hard error at import time. See
[plans/modules-folder.md](../plans/archive/modules-folder.md).

Note that `examples/modules_demo/` has a `modules/` folder of its own and is
therefore unaffected by this one: the nearest root wins.

## The MODULE file

Every module here should carry a `MODULE` file. It is **informational**: nothing
in the compiler reads it, and `requires` is a record of what the module was built
and tested against rather than a constraint.

```text
name     mongo
version  0.1.0

requires bson 0.3.0
```

The author owns `name` and `version`. The `requires` block is regenerated by
`yoopdist` and should not be hand-edited.

## Shipping one

[tools/yoopdist](../tools/yoopdist) builds the directory a user installs:

```sh
yoopdist modules/mongo /path/to/dist
```

It copies the `.yoop` sources and the tests, skips any `modules/` directory,
and rewrites the `requires` block from the imports it actually finds. A user
drops the result into their program's `modules/` folder and can run
`yoopiler --test .` against it to confirm the install works on their machine.

## Adding one

1. Create `modules/<name>/` with every `.yoop` file declaring `module <name>;`.
2. Write a `MODULE` file with `name` and `version`.
3. Add `<name>.test.yoop` beside the source. It is excluded from the module's
   own source files, so it imports the module the way a consumer does:
   `import * as m from "modules/<name>";`.
4. If it binds a C library, declare it with `extern "C" from library "..."` and
   document what the user must install. Do not vendor the C sources.
