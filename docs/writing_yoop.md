# Writing Yooperlang

The current best practice for writing Yoop code: std, the compiler itself,
tools, and example programs.

**This document wins.** Where an older example or a stray comment disagrees with
this file, this file is right. If you find something here that is actually
wrong, fix it here first.

Scope: how to WRITE Yoop. For how the compiler is built internally (module map,
layer boundaries, codegen rules), see
[../bootstrap/README.md](../bootstrap/README.md).

## 1. Non-negotiables

The short list. Most broken builds are one of these.

1. **Std value imports must be namespaced.**
   `import * as vec from "std/core/vec.yoop";` then `vec.vecNew(0)`.
   `import { vecNew } from "std/..."` is a hard error for functions and consts.
   Types, traits, kinds, enums and unions are exempt and may be imported by
   name (`import { Vec } from "std/core/vec.yoop";`).
2. **Imports come first in a file**, before any declaration.
3. **A struct literal cannot be typed on its own.** `Foo { x: 1 }` needs a
   target: an annotated binding, a return, or a call argument. A bare
   `let f = Foo { x: 1 };` fails.
4. **Every path must return.** The compiler proves this; `while (true)` with no
   escaping `break` counts as diverging.
5. **No nested functions and no closures.** Declare at module scope. A function
   value is a plain function pointer, and it captures nothing.
6. **A bare `{ ... }` block is not a statement.** Blocks belong to a function, an
   if/else, a loop, a switch arm, or a block-owning kind.
7. **`ref` is explicit at both ends.** `function f(x: ref T)` is called as
   `f(ref x)`.
8. **Trait methods are called trait-qualified**: `Display.toString(ref x)`, never
   `x.toString()` and never bare `toString(ref x)`.
9. **A struct used as a variant payload must be declared before the variant**, in
   the same file. Otherwise you get a misleading "type has no field" error.

## 2. Naming and files

- **Files and directories: `snake_case`.** `scan_tables.yoop`,
  `source_graph/`. This is the one place underscores belong.
  Module names are the exception forced by the directory-module rule: a module
  name matches its folder, so prefer single words (`http`, `net`, `cancel`).
- **Types and type-like declarations: `PascalCase`.** struct / `type`, `trait`,
  `variant`, `enum`, `union`, `vtable`, type parameters, and variant case names
  (`Result.Ok`, `Option.None`).
- **Functions, methods, locals, parameters, struct fields, kind names:
  `camelCase`.** Including std: it is `vec.vecNew`, `map.mapGet`,
  `str.stringConcat`, `Display.toString`. There are no `snake_case` spellings
  (`vec_new`, `map_get`, `to_string`) anywhere in std.
- **`SCREAMING_SNAKE`: value-`enum` case names and module-level `const`s.**
  `TokenTags.EOF`, `ASTNodeKind.FUNCTION_DECL`, `SEEK_SET`. Note `const` is
  overloaded: a module-level constant is `SCREAMING_SNAKE`, a local `const`
  binding is `camelCase`.
- **Never `snake_case` for an identifier.** The underscore is still legal in the
  grammar; convention does not use it.

Two deliberate carve-outs, both the same rule (mirror the C side exactly so a
reader can match it against a man page or a header):

- **`extern "C"` blocks keep the real C symbol names** (`sqlite3_prepare_v2`,
  `yoop_arena_new`). These are link-level names, not style choices.
- **A struct that mirrors a C ABI struct keeps the C field spellings**
  (`sin_family`, `sin_addr` in `std/net/socket.yoop`).
- The `c_*` integer aliases (`c_int`, `c_ssize_t`) stay as they are for the same
  reason.

Indentation is 2 spaces in all new code.

Two corners of the tree do not follow the rules above (do not add more, do not
feel obliged to fix them as part of unrelated work):

- Tool-internal helpers in [../tools/](../tools/) are `snake_case` (about 30
  names across yoopbinder / yoopdist / stdindex).
- Example-local helper functions under [../examples/](../examples/) are a mixed
  corpus.

## 3. Memory, strings, and allocators

This is where old examples mislead most often.

### 3.1 `string` versus `Text`

The split is ownership, and it is the single most important distinction to get
right:

- **`string` is the BORROWED view.** A nul-terminated `char *`. One pointer, no
  length, never freed by you. Literals are strings. It is what you pass to
  anything that only READS. `s.len` is a `strlen` call, so it is O(n) every
  time; do not call it in a loop condition.
- **`Text` is the OWNED, growable buffer** ([../std/core/text.yoop](../std/core/text.yoop)).
  It allocates through the ambient allocator, captures that allocator so it frees
  back into the same one, and is `disposable` so cleanup is injected for you.

```yoop
import * as text from "std/core/text.yoop";
import { Text } from "std/core/text.yoop";
import { disposable } from "std/core/kinds.yoop";

disposable greeting: Text = text.fromString("hello");
text.push(ref greeting, ", world");
printf("%s\n", text.view(ref greeting));   // borrow back out, no copy
                                           // dispose fires at scope end
```

**Prefer `std/core/text.yoop` for anything that builds or inspects a string.**
It is the allocator-aware API and it is explicit about bytes versus
codepoints: anything named `...Bytes` or taking an offset works in BYTES,
anything named `...Char` / `chars` works in Unicode codepoints.

`std/core/strings.yoop` is the bare-`string` API. Reach for it only for
what `text` does not cover: `split`, `stringHash`, `padStart` / `padEnd`,
`lastIndexOf`, `stringFromBytes` (the UTF-8 VALIDATING constructor),
`stringConcatAll`, and `strFree`.

**Know this before you mix them:** `strings.yoop` allocates through
`intr.heapAlloc`, which is raw `malloc`. It does **not** route through the
allocator context. So `str.stringConcat(...)` inside an arena scope comes from
malloc, is not reclaimed when the arena dies, and leaks unless you `strFree` it.
`Text` does route through the context. If you are working inside an arena, use
`Text`.

**A `string` you BUILD leaks. Build with `Text` instead.** This is the single
easiest way to write a leak in this language, because nothing warns you:

- Every template literal (`` `${a}: ${b}` ``) is a fresh malloc.
- So is every `str.stringConcat` / `stringConcatAll` / `padStart` / `sliceFrom`,
  and every `format.intToString` / `uintToString`.
- `disposable` on a `Vec<string>` frees the VECTOR, never the strings in it.
- `--track-heap` cannot see any of it - it only counts `heapAlloc`, and a string
  is a direct `malloc` inside `stringFromBytesUnchecked`. Use `leaks --atExit --
  ./prog` on macOS to see the truth.

The rule that follows: **anything that accumulates text in a loop uses a
`Text`**, not a `Vec<string>` plus a join, and not repeated concatenation. Use
`text.push`, `text.pushByte`, `text.pushUint` / `text.pushInt` (which format
digits straight into the buffer, so a number costs no allocation at all), and
`text.view` to borrow the result back out.

```yoop
// leaks one string per line, plus one per interpolated number
disposable lines: Vec<string> = vec.vecNew(64);
vec.vecPush(ref lines, `  ret i32 ${value}\n`);
return str.stringConcatAll(vec.vecAsArray(ref lines));

// leaks nothing, and is reclaimed by an enclosing arena
disposable out: Text = text.make(1024);
text.push(ref out, "  ret i32 ");
text.pushUint(ref out, value);
text.pushByte(ref out, '\n');
return text.view(ref out);   // a borrow; the Text owns the bytes
```

**Arguments are eager, so an assert or log message ALLOCATES even when nothing
is wrong.** This is the sneakiest version of the rule, because the line looks
free:

```yoop
// formats and mallocs on EVERY call, passing or not
debug.assert(pos <= src.len, `pos ${pos} is outside src length ${src.len}`);

// builds the message only when it is actually needed
if (pos > src.len) {
  debug.assert(false, `pos ${pos} is outside src length ${src.len}`);
}
```

One such line in the bootstrap's `posToSourceLocation`, which runs once per AST
node, was 814 of the 1855 leaks in a single compile. The same applies to
`log.info(...)` on a hot path.

Measured, so it is not theoretical: the bootstrap compiler built its IR emitter
the first way and leaked roughly 1KB per line of input - 3266 leaks and 244KB to
compile a 203-line program. Moving codegen and the token dump to `Text`, plus
guarding that one assert, took it to 632 leaks and 131KB with no behaviour
change. Nothing in `std/`, `examples/` or `bootstrap/` frees a string today.

A single short-lived string (one diagnostic message, one name) is not worth the
ceremony - a process that exits reclaims it. The rule is about LOOPS and
accumulation.

`string == string` does not compile (it is a typecheck error). Use
`text.equals(a, b)` or `str.stringEq(a, b)`. The only string comparison the
language does natively is between `enum<string>` cases, which lowers to a
pointer compare and works because identical literals are interned.

### 3.2 Containers

- `Vec<T>` ([../std/core/vec.yoop](../std/core/vec.yoop)) is the growable array:
  `vecNew`, `vecPush`, `vecGet`, `vecSet`, `vecClear`, `vecAsArray`,
  `vecExtendFrom`, `vecFromArray`, and `vecIter` for `for x in`.
- `Vec<T>` and `Text` are **container-owned**: each captures the allocator that
  was current when it was built and routes every later grow AND the final free
  back through that same one, whatever is ambient at the time. A Vec built inside
  an arena frees into the arena even if it grows after the arena stopped being
  current.
- `Map<K, V>`, `Set<K>`, `Deque<T>` are in [../std/collections/](../std/collections/).

### 3.3 Allocators and arenas

The current allocator is ambient, held per-thread (per-TASK inside a task).
`std/core/alloc.yoop` owns it. Two canonical scoped forms:

```yoop
import * as mem from "std/core/alloc.yoop";
import { ephemeral, disposable } from "std/core/kinds.yoop";

// (a) Install an EXISTING arena for a region. Anonymous - nothing to name.
ephemeral mem.allocatorScope(ar) {
  let t: Text = text.fromString("comes out of ar");
}                                  // pop fires at the brace

// (b) Make a NEW arena, name it, and tear it down at the brace.
disposable reg: mem.ArenaScope = mem.arenaScope(4096) {
  let p: unsafe_ptr<void> = mem.allocBytes(64, 8);
  let used: usize = mem.arenaUsed(reg.arena);
}                                  // pop + destroy fire at the brace
```

Use (a) when the arena outlives the region (a per-request reset against a
long-lived arena). Use (b) when the arena IS the region.

**Temp storage** is the scratch arena: `mem.tempAllocator()` to allocate,
`mem.resetTemp()` once at a boundary. It belongs to the TASK when you are inside
one and to the thread otherwise, so a task's scratch is invisible to every other
task and `resetTemp()` inside a task can never clear storage belonging to whoever
dispatched it.

Raw escape hatches, for when you genuinely mean malloc: `intr.heapAlloc<T>(n)` /
`intr.heapFree`. Context-routed siblings: `intr.ctxAlloc` / `intr.ctxFree`. All
require `import * as intr from "std/core/intrinsics.yoop";`.

**Allocation failure is not checked.** An exhausted arena or a failed malloc
returns null and you dereference it. There is no diagnostic. Size arenas
generously.

## 4. Kinds

Kinds are the language's distinguishing feature, and the thing most likely to be
misremembered. Read this section before writing a kind.

### 4.1 What is advisory, what has teeth

- **Ownership is advisory and silent by default.** `propagates<K>` on a type
  DOCUMENTS that bindings of it own a resource. It does not force the user to do
  anything, there are no unsatisfied-obligation errors, and returning a
  propagating value never requires the function to declare anything.
- **Auto-cleanup is the opt-in with teeth.** Write the kind keyword on the
  binding and the compiler injects the cleanup call at scope end:
  `disposable t: Text = ...` calls `dispose`, `joined h = ...` calls `join`,
  `pooled h = ...` does the refcount release. If you already called the method by
  hand on every path, no second call is injected.
- **Marker / clearance kinds are a real static check.** A `conferred` kind cannot
  be forged (a sink that names it requires it); a `restrictive` kind cannot be
  silently dropped (a plain slot forbids it). Transitions must go through the
  trait method the kind decl names via `clearedBy` / `appliedBy`. Free functions
  cannot launder. This is what `owned` (on strings) and `cleared` (in the
  yooperdoom gate) are built on.
- **Escape analysis has teeth.** `mustNotEscape scope` is enforced, and it is
  also what lets the compiler put a binding in a stack slot.

Avoiding a double free is the `dispose` implementer's job: make `dispose`
idempotent (free, then null the field; guard on null).

### 4.1a The `unhandled-disposable` warning, and why it is opt-in

`--warn-disposable` turns on a warning for a binding that carries a cleanup
obligation nobody handles: no kind keyword, no manual dispose, not returned, not
passed on by value. It is **off by default in a build** and **on in the language
server** (`yoopiler_boot --lsp`), which is where an advisory belongs: the reader
can see the line it is about, and the server only ever publishes what the file
in front of them says.

It is worth running when you suspect a leak - it found one in the bootstrap
driver (`let prog = typecheckProgram(...)`, which owns the type and symbol
arenas) that had been invisible. Two things it cannot tell apart from a real
leak, which is why it is not on by default:

- **An arena scope.** Inside `ephemeral mem.allocatorScope(ar) { ... }` NOT
  disposing is the whole point - the arena reclaims it. The compiler has no way
  to know it is in an arena: `yoop_cur_alloc` is thread-local runtime state, and
  it is already unsound across an `await` (a task can resume on another worker),
  so a static "you are in an arena" claim would be a lie in the async path.
- **A copy read out of a container.** `let x = vec.vecGet(ref v, i)` copies a
  value the Vec still owns; disposing it would double-free. Distinguishing this
  from a real leak needs move analysis, which the advisory ownership model
  deliberately does not have.

`ref x` is a borrow and never counts as handling the obligation; passing `x` by
value does, because the callee may have taken it.

### 4.1b Never RETURN a `disposable` binding

This is the easiest way to write a silently broken program, because the broken
version looks completely correct and the compiler says nothing.

```yoop
// WRONG. Compiles clean, runs, and hands back freed storage.
function build(n: usize): Result<Text, string> {
  disposable out: Text = text.make(n);
  text.push(ref out, "xxx");
  return Result.Ok { value: out };     // dispose already fired at scope end
}                                      // caller sees an empty Text
```

`disposable` means "clean this up when THIS scope ends". A value you hand back
outlives this scope, so it is not yours to clean up. The idiom std uses
everywhere is a plain `let` plus `propagates<disposable>` on the return type:

```yoop
// RIGHT. `propagates<disposable>` documents that the RESULT owns a resource.
function build(n: usize): Result<Text, string> propagates<disposable> {
  let out: Text = text.make(n);
  text.push(ref out, "xxx");
  return Result.Ok { value: out };
}
```

The rule: **`disposable` on a binding you consume here; a plain `let` plus
`propagates<disposable>` on the signature when you hand ownership back.** Every
producing function in `std/core/text.yoop` and `std/core/vec.yoop` follows this
(`text.concat`, `text.join`, `vec.vecFromArray`); copy them.

### 4.2 A `disposable` binding is const on purpose

```yoop
disposable buf: Buf = bufNew();       // const: cannot rebind
let disposable buf: Buf = bufNew();   // mutable, and you own the consequences
```

The injected cleanup fires ONCE, at scope end, on whatever the binding holds at
that moment. So rebinding silently drops the outgoing value without disposing it.
Const by default makes that impossible by accident; `let` is the informed opt-in,
and it comes with the rule "dispose the old value before you overwrite it".

### 4.3 When to reach for a kind

Every kind in this codebase encodes the same shape: **"if you have a value of
this type, something has happened to it, or something must happen to it."**
`disposable` says the value owns heap state that has to be cleaned up;
`joined` / `pooled` say who is responsible for waiting on a task's result. When
you catch yourself writing that sentence in a comment, in a "you must call X
first" doc line, or in a parameter named `safe_*` / `unchecked_*` /
`validated_*`, that is a kind asking to exist.

Reach for one when at least two of these hold:

- The obligation has to survive a function boundary: a return, a struct field, a
  task spawn.
- The proof and the use site are in different modules.
- A reasonable caller could skip the obligation and nothing would notice.
- The obligation has a discrete discharge point (a method to call, a scope to
  close, a transfer to perform), not a vague "be careful".

When two hold it is borderline: lean toward the kind for std and for
cross-module APIs, toward plain validation for a one-off program.

Do NOT reach for one when:

- The proof and the use are in the same function. Plain code is clearer; you can
  see both ends.
- The obligation reduces to "be a well-formed T". That is what the type is for,
  and a kind layered on a type that already excludes the bad cases is noise.
- You want three kinds for three slightly different states of one value. That is
  an enum (states) or a state machine (transitions), not kind soup.
- The discharge is not a single discrete event. No kind can encode "use
  carefully"; the answer there is a narrower type or a different API.

Four shapes that are a kind wearing a disguise: a `validate*` / `assert*` /
`check*` function that returns its input unchanged on success; a parameter whose
NAME carries the obligation; a "this MUST be called before X" comment; and a
defensive re-check on entry to a function of something the caller was supposed
to have done.

Adding one costs a declaration, a discharging trait or scope rule, an update to
every function that produces or consumes the type so the kind threads through,
and a fail fixture proving the compiler rejects the unsatisfied case. It earns
that back when it kills a class of "did I forget to validate" bugs across
several consumers, which is why std APIs usually justify it and one-off programs
usually do not.

To add one:

1. Decide where it lives. Cross-cutting kinds (used by std and by programs) go
   in [../std/core/kinds.yoop](../std/core/kinds.yoop); a program's own kinds
   live in its own module. Kinds are not privileged to std.
2. Declare the kind, and the trait that discharges it if it needs an active
   discharge (`disposable` pairs with `Disposable`, `joined` / `pooled` with the
   task-shape traits).
3. Document the discharge sites. A kind with no clear "this call satisfies it"
   is the kind-soup anti-pattern.
4. Add both fixtures: a passing program under [../examples/pass/](../examples/pass/)
   showing the happy path, and a failing one under
   [../examples/fail/](../examples/fail/) showing the compiler reject the
   unsatisfied case.
5. If it changes a cross-cutting invariant (propagation, transfer, escape), say
   so in section 4 here, so the ownership model stays one document.

`appliesTo region` kinds (`ephemeral`) govern a lexical block with no named
value: allocator scopes, pushed contexts, transaction guards. They MUST declare
`ownsBlock` and may not also name a value site.

## 5. Errors as values

There are no exceptions. Fallible functions return a `Result`-shaped variant
(`std/core/types.yoop` has the generic `Result<T, E>` and `Option<T>`).

```yoop
function parseHead(buf: uint8[]): Result<Request, HttpError> {
  const line = readLine(buf)?;              // propagate Err unchanged
  const target = splitTarget(line)? "target";   // prepend context to the error
  ...
}
```

Three forms of `?`:

- `expr?` propagates the `Err` unchanged. The enclosing function must itself
  return a fallible variant.
- `expr? "context"` prepends a string (or template literal) to the propagated
  error. For a `string` payload the compiler concatenates; for a structured
  payload the type implements `WithContext<T>`.
- `expr? e { ... }` HANDLES the failure here instead of propagating, binding the
  `Err` payload to `e`. **The block must diverge on every path** (return, break,
  continue, or a diverging switch), because it runs instead of producing a value.
  This form does not require the enclosing function to be fallible, which is what
  makes it usable in `main` or in a handler that returns a plain value.

Carry the status the caller needs on the error type itself. `HttpError` carrying
its own status code is what lets a failure detected deep in a parse surface as a
400 instead of a blanket 500.

Known limitation: call-site inference cannot see through a generic enum's type
arguments, so `function bridge<T>(r: Result<T, string>)` will not infer `T` from
a `Result<int32, string>` argument, and there is no turbofish to say it out loud.
The workaround is one small bridging helper per payload type.

## 6. Async and concurrency

**`async` is a real color and the rules are enforced.** An `async` function
lowers to an LLVM coroutine; `await` is the only way to call one, and `await` is
only legal inside another `async` function or a `task` body.

- `task f(): T` evaluates to `Task<T>` at the call site (a SPAWN, not an await).
- `wait h` BLOCKS a thread. `conc.awaitTask(h)` SUSPENDS a task. **Inside a task
  body only the second is legal** and `wait` is rejected outright.
- "Await all" is an ordinary loop over `awaitTask`; each iteration frees the
  worker, and completion order does not change the answer.
- An `async` function that never awaits just runs straight through on its first
  step. So an in-memory implementer of an async trait method simply declares
  `async` and never suspends.

`std/net` and `std/http` are async top to bottom, so anything calling into them
is async too. Two deliberate stopping points keep the coloring from spreading:
**`Handler.handle` stays synchronous** (it takes a buffered request and fills a
response) and **`Writable.flush` stays synchronous**.

The sync/async bridge at the top of a program is: `main` spawns a `task`, then
`wait`s it.

Note `serve()` handles one connection at a time. For real concurrency, spawn a
task per connection over the exported `serveConnection`.

## 7. Modules and imports

- **A module is a single file OR a directory of files that each declare
  `module <name>;` as their first line.** Directory modules today:
  `std/core/cancel/`, `std/db/sqlite/`, `std/net/`, `std/http/`, `std/tls/`.
- Inside a directory module, **declarations are shared but imports are not.**
  Siblings see each other's declarations whether exported or not (that is the
  point: it is how a module gets real privacy). But using a name that only a
  sibling imported is an error.
- **Import the module, never one of its files**: `from "std/http"`, never
  `from "std/http/server.yoop"`.
- `import.unsafe;` and `import.test;` are PER SOURCE FILE, not per module. That
  is what lets one file in a directory module name `unsafe_ptr` while its
  siblings may not.
- `modules/<name>` is the program-owned import root for non-std code, resolved by
  walking up from the IMPORTING file to the nearest `modules` directory.
  Dependencies are FLAT and nesting is a hard error.

## 8. Testing Yoop code

Testing has no compiler-baked semantics: `test`, `suite` and `assert` are
ordinary kinds and functions in [../std/test.yoop](../std/test.yoop), and all
three remain usable as identifiers.

- A test module is `*.test.yoop`, declares `import.test;` as its first line, and
  has no `main`.
- A suite is a top-level function carrying the `suite` kind.
- A case is a `test`-kind binding whose block records its outcome at the closing
  brace.

```yoop
import.test;
import * as t from "std/test.yoop";
import { suite, test, Case } from "std/test.yoop";
import { strangeAdd } from "./strange_add.yoop";

suite function addsStrangelyWhenFirstIsTwoModFive(): void {
  let test theory: Case = t.asserts("adds an extra 1 when a % 5 == 2") {
    const got = strangeAdd(2, 2);
    theory.isSuccessful = got == 5;
    theory.detail = `strangeAdd(2, 2) gave ${got}, wanted 5`;
  }
}
```

**An assertion is a bool plus a string, deliberately not a comparison.**
`isSuccessful` is the outcome and `detail` is reported only on failure. There is
no `equals(got, want)` primitive because two operands flatten the context that
made the check meaningful. Write helpers as ordinary Yoop functions when a shape
repeats.

Run with `yoopiler_boot --test .`, optionally with filters as extra positionals
(`yoopiler_boot --test . addsPlainly`). Suites are the unit of isolation (each runs
inside an arena scope); cases are the unit of reporting. Exit code is the failure
count.

Fixtures live in [../examples/testing/](../examples/testing/). Do NOT put
`*.test.yoop` under `examples/pass/`, which is compiled as ordinary programs.

## 9. Compiler conventions

The compiler lives in [../bootstrap/src/](../bootstrap/src/) and compiles
itself.

- The module map is in [../bootstrap/README.md](../bootstrap/README.md). The
  ownership model it follows is section 4 above.
- Layer boundaries: module graph -> lex -> parse -> typecheck -> codegen. There
  is no intermediate IR; codegen consumes the typed AST directly.
- **One directory module per layer**, each a handful of small files:
  `diagnostics`, `lex`, `ast`, `parse`, `source_graph`, `typecheck`, `codegen`,
  `link`, `utils`. A layer's vocabulary lives WITH that layer - there is no
  shared types file, and wanting one is a sign the type belongs to a layer
  already.
- The AST is an **arena plus NodeId indices**, not a tree of pointers: a fat node
  with `childA/B/C` slots and list-node indirection, NodeId 0 reserved as null.
  Build with the scratch-Vec-then-splice pattern.
- Decoration goes in SIDE TABLES keyed by NodeId, not as mutable fields on nodes.
- Every change ships tests: a `*.test.yoop` beside the module for anything
  checkable without a binary, a fixture in `../bootstrap/tests/slice/` for
  anything that has to reach an executable, and a program under
  `../examples/pass/` or `../examples/fail/` for a language-level behaviour. An
  `.expected` file is written by hand from what the program should do, never
  captured from what the compiler currently prints.

## 10. Sharp edges

These are things that will cost you time; none is a reason to avoid the
feature.

- **Returning a `disposable` binding silently hands back freed storage.** No
  diagnostic, no crash, just wrong data. This is the direct cost of the advisory
  ownership model and it is the most likely mistake to make. See 4.1b.
- **An unpinned literal can reach codegen.** `const big = 3000000000 * 3000000000;`
  fails with an "internal ... this is a compiler bug" message. It has a span and
  names the workaround (bind to a local with an explicit type annotation first),
  but it is still an internal error rather than a type error.
- **Allocation failure is a null dereference.** No check, no diagnostic. See 3.3.
- **`string == string` does not compile.** Use `text.equals` / `str.stringEq`.
- **Bare `string` ignores the allocator context.** See 3.1.
- **Generic inference does not see through generic enum type arguments**, and
  there is no turbofish. See section 5.
- **A `keyword`-ish identifier can still surprise you.** Some words that read as
  keywords are contextual and legal as identifiers (`module`, `test`, `suite`,
  `signature`, `enumerable`, `conferred`, `clearedBy`); a few real keywords
  cannot be used as parameter names.
- **`@derive(display)` does not work on generic types** (generic structs or
  variants), and it cannot recursively expand a field whose type does not itself
  derive Display. Both are clear errors, not silent wrong output.
- **Trait method dispatch needs a concrete struct receiver in a few places.**
  `Dispatcher.from(ref h)` stores a POINTER to `h`, so the handler must outlive
  the route table, and it rejects a type parameter.

## 11. Quick reference

```yoop
// imports first, std values namespaced, types by name
import * as vec from "std/core/vec.yoop";
import { Vec } from "std/core/vec.yoop";
import * as text from "std/core/text.yoop";
import { Text } from "std/core/text.yoop";
import * as mem from "std/core/alloc.yoop";
import { disposable, ephemeral } from "std/core/kinds.yoop";
import { Result } from "std/core/types.yoop";

type Point {
  x: int32,
  y: int32,
}

trait Shape {
  function area(ref self): int32;
}

// `out` is handed back, so plain `let` + propagates<disposable> on the
// signature. `items` is consumed here, so it takes the `disposable` keyword
// and its cleanup is injected at the closing brace.
function build(n: usize): Result<Text, string> propagates<disposable> {
  let out: Text = text.make(n);
  disposable items: Vec<int32> = vec.vecNew(n);
  for (let i = 0; i < n; i += 1) {
    vec.vecPush(ref items, 1);
  }
  for it in vec.vecIter(ref items) {
    text.push(ref out, "x");
  }
  return Result.Ok { value: out };
}
```
