A small systems language with a TypeScript feel.

Yooperlang started as one idea I wanted to try: put more context about how a value is used into the code itself, and see whether that makes systems programming easier to follow coming from the garbage collected web world. That context is the kind layer. Everything around it is a deliberately small language: structs plus free functions, traits, no GC, LLVM IR out and a native binary from clang.

import * as text from "std/core/text.yoop";
import { Text } from "std/core/text.yoop";
import { disposable } from "std/core/kinds.yoop";
import { Result } from "std/core/types.yoop";

type Town {
  name: string,
  population: int32,
}

// Errors are values: no exceptions, no null. `?` unwraps the Ok and
// returns the Err from the enclosing function, with a context string
// that is only built on the failure path.
function census(t: ref Town): Result<int32, string> {
  if (t.population < 0) {
    return Result.Err { error: "negative population" };
  }
  return Result.Ok { value: t.population };
}

function describe(t: ref Town): Result<int32, string> {
  const n = census(t)? "reading the census";

  // `disposable` is a kind, and a kind attaches to the BINDING, not
  // the type. It makes the compiler place the cleanup call on every
  // path out of this scope, including the one `?` above takes.
  disposable line: Text = text.make(64);
  text.push(ref line, t.name);
  text.push(ref line, ": ");
  text.pushInt(ref line, int64(n));
  printf(`${text.view(ref line)}\n`);

  return Result.Ok { value: n };
}

function main(): int32 {
  let marquette: Town = { name: "Marquette", population: 20629 };
  switch (describe(ref marquette)) {
    case Result.Ok { value: n }: { return 0; }
    case Result.Err { error: e }: { printf(`failed: ${e}\n`); return 1; }
  }
}

Three layers, kept separate

A type is what a value is, a trait is what it can do, and a kind is how a binding is used. Most languages mix the third into the other two. Keeping it apart is the whole experiment. Pick one:

How it reads day to day

errors
A fallible function returns Result<T, E>. ? unwraps the Ok and returns the Err, and only compiles where the error can be carried onward. ? "context" builds its message on the failure path only.
concurrency
task is a kind on a function, so every call is a spawn and no async keyword colors the API. The binding decides where the wait happens: joined at the closing brace, pooled whenever you ask.
cleanup
Write dispose once on the type that owns the resource. Every disposable binding gets the call placed on every exit path. No destructors, no defer, no wrapper types.
interop
extern "C" from library "SDL2" { ... } and the linker does the rest. C is the bridge while the Yoop-native library is still small.

Where it actually stands

A personal project by someone who is not a compiler engineer, so here is the state of it without a coat of paint.

self hosting
The compiler is written in Yoop and is the only compiler for the language. It builds itself, and the release refuses to package unless stage2 and stage3 come out byte-identical.
what works
Structs, traits, kinds, generics with bounds, variants with exhaustive switch, errors as values, tasks, vtables, C interop, DWARF debug info, and a standard library with HTTP, TLS, SQLite, crypto and collections. 245 example programs are compiled by the test suite.
what is rough
Allocation failure is a null dereference with no diagnostic. A built string ignores the allocator context and leaks unless you use Text. Returning a disposable binding hands back freed storage with no warning. Generic inference cannot see through a generic enum's type arguments.
what it is not
Not a borrow checker. Kinds do some of what lifetimes do, and the trade is explicit: you keep more memory-safety responsibility in exchange for a shorter on-ramp.

Or build it yourself

git clone https://github.com/tkarnau/yooperlang.git
cd yooperlang

YOOP_STD_ROOT=$PWD/std YOOP_RUNTIME_ROOT=$PWD/runtime \
  $(node scripts/seed.mjs) examples/tour/hello.yoop -o /tmp/hello
/tmp/hello

Needs clang on your PATH, plus Node 22 or newer to run the script that fetches the seed compiler. The compiler is written in Yoop, so a build starts from a previously released binary; scripts/seed.mjs downloads one on first use.

Borrowed from better languages

None of this is original research. C interop with no shim and compile-time evaluation come from Zig. Result, ? and traits-as-the-only-polymorphism come from Rust. Types on the right and inferred when obvious come from TypeScript. Value semantics with an explicit ref come from Swift. A small core and fast compiles come from Go. The kind layer is the one part I have not seen elsewhere in this shape, and whether it is a good idea is what I am still finding out.
