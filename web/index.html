A systems language for folks who got stuck writing web apps.

I've spent my career in JavaScript, TypeScript, C#, and Node - shipping CRUD apps and APIs. Every time I tried to pick up a real systems language, I bounced off the cliff face of dense syntax and missing context. So I'm building Yooperlang: a systems language with a TypeScript feel, no garbage collector, and code that's actually readable if you came up on the web side.

A taste

Two concurrent task calls, errors as values with ?, a switch over the result variants - and not an async or await in sight. Still compiles to a native binary with no garbage collector. If you've written TypeScript, the shapes should still feel familiar. 

import { Result } from "std/core/types.yoop";

// `task` says every call to fetch() spawns a concurrent worker.
// The return type is a Result - any Ok/Err enum participates in `?`.
task fetch(url: string): Result<int32, string> {
    if (url.len == 0) {
        return Result.Err { error: "empty url" };
    }
    return Result.Ok { value: url.len };   // pretend network here
}

function total(a: string, b: string): Result<int32, string> {
    joined ra = fetch(a);                  // spawned now
    joined rb = fetch(b);                  // also spawned - running in parallel
    // `wait` reads each task's result; `?` bails to the caller on Err.
    return Result.Ok { value: (wait ra)? + (wait rb)? };
}

function main(): int32 {
    switch (total("hello", "yoop")) {
        case Result.Ok  { value: n }: printf(`total=${n}\n`);
        case Result.Err { error: e }: printf(`failed: ${e}\n`);
    }
    return 0;
}

Why bother?

The gap between web devs and systems devs keeps getting wider. Every year there's another framework, another runtime, another layer of abstraction - and every year the machine underneath gets a little further away. Performance gets traded for ergonomics, and ergonomics gets traded for "developer experience" that mostly means more layers.

I miss the idea that one person could write the whole thing. Yooperlang is a small push in that direction - a language that web folks can pick up without feeling like a simpleton, and that's still close enough to the metal to actually be fast.

About the name: the author is from the Upper Peninsula of Michigan, and "yooper" is a funny word. That's the whole story.

Heads up: I'm not a compiler designer. This is my first real swing at a language beyond a toy project. The pitch isn't "this is the best systems language ever made" - it's "maybe folks like me deserve a path back to the fun stuff." If that resonates, stick around. It's more fun with company.

Three layers, kept honest

Type

What the value is - the concrete shape of data. int32, Point, FileHandle.

Trait

What the value can do - operations it supports. Disposable, Iterable<T>, Task<T>.

Kind

How the binding must be used - lifecycle and scoping rules. disposable, scoped, pooled.

How it stacks up against languages you might already know

Yooperlang isn't trying to dethrone anything. It sits in the gap between languages I already use. Here's the short version of what's different.

vs TypeScript

The syntax feel is on purpose - types on the right, structs, no classes, template literals with ${...}. But TypeScript erases types at runtime and rides on a garbage-collected VM. Yooper compiles to a native binary, keeps types around for codegen and lifecycle enforcement, and ships no runtime worth mentioning.

Also: types are nominal, not structural - type Meters { v: int32 } and type Seconds { v: int32 } aren't the same type, even though they have the same shape. And there's no null or undefined; absence is modeled explicitly with an enum variant or a validity field.

vs C++

Same target - native, fast, low-level access when you need it - without the surface area that pushes web folks away. No header files. No preprocessor. No template metaprogramming maze. No rule of five.

Memory cleanup is declarative: tag a binding with the disposable kind and the compiler emits the cleanup call at scope end. You write dispose once on the type that owns the resource; every caller gets the cleanup for free. No constructor / destructor pairs, no RAII wrapper types, no std::unique_ptr ceremony.

vs Rust

A lot of the good Rust stuff is here on purpose: errors as values via Result<T, E>, the ? operator with Into<T> conversions on mismatched error types, traits without inheritance, no GC, monomorphized generics, sum types via enum.

What's not here: the borrow checker, named lifetimes, and the Box<dyn Trait> dance. Kinds do a lot of what lifetimes do in Rust - they're a usage contract on the binding (disposable, joined, pooled, propagates<K>) rather than an inferred lifetime parameter that travels with every reference. Runtime trait polymorphism is opt-in via a named vtable Reader for Readable { ... } shape, not a magic dyn.

The trade is honest: Yooper accepts some memory-safety responsibility back onto the developer in exchange for a much shorter on-ramp. If you've bounced off Rust's borrow checker and wanted the rest of Rust without the fight, that's the lane.

Ideas borrowed from other languages

None of this is original research. I'm a working developer who liked some ideas in other modern languages and stitched them together into something that fits the way I want to write code. Credit where it's due:

  • Zig - compile-time evaluation with @precompile (constants and small tables folded into the binary), direct C ABI interop with no FFI shim, and the idea that "async coloring" shouldn't infect the type system. Yooper expresses "this function spawns" via the task kind instead of an async keyword, and call sites pick the wait strategy on the binding (let joined, let pooled).
  • Rust - Result<T, E>, the ? operator, traits as the only polymorphism mechanism, no nulls, and the general attitude that errors should be visible at the call site.
  • TypeScript - types on the right, inferred when obvious, optional when not. The whole expression-level feel of a modern web language.
  • Swift - value semantics by default, ref only where you mean it, and the convention that capability-shaped things (Disposable, Iterable<T>) live in a separate layer from data.
  • Go - small core, unsurprising standard library, and the conviction that fast compiles are worth designing the language around.

The actual original-ish piece is the kind layer - treating lifecycle, scoping, concurrency mode, and propagation as one orthogonal mechanism instead of five unrelated keywords. Whether that turns out to be a good idea is something I'm figuring out as I go.

What you can build today

These aren't promises about a future version - the snippets below are excerpts from real programs in the repo.

An HTTP server

The handler shape borrows the comfort of Express-style request/response objects, but everything underneath compiles down to native code. The disposable kind on the listener means cleanup happens at scope end, automatically - no try/finally, no defer. 

import { disposable } from "std/core/kinds.yoop";
import { tcp_listen, ListenResult } from "std/net/tcp.yoop";
import { serve_n, Handler, HandleOutcome } from "std/http/server.yoop";
import { Request, Response, ok, headers_add } from "std/http/types.yoop";

// User-defined handler. std/http/server is generic over any type
// that implements the Handler trait.
type HelloHandler implements Handler {
    greeting: string,
    function handle(ref self, ref req: Request, ref resp: Response): HandleOutcome {
        resp.status = ok();
        headers_add(ref resp.headers, "Content-Type", "text/plain");
        resp.body = string_as_bytes(self.greeting);
        return HandleOutcome.Ok;
    }
}

function main(): int32 {
    // host, port, backlog. `disposable` drops the socket at scope end.
    let disposable lr: ListenResult = tcp_listen("127.0.0.1", 18080, 128);

    // No try/catch in this language - inspect the error field directly.
    if (lr.error.len > 0) {
        printf(`bind failed: ${lr.error}\n`);
        return 1;
    }

    let handler: HelloHandler = { greeting: "Hello, World!\n" };
    serve_n(ref lr.listener, ref handler, 0);  // 0 = serve forever
    return 0;
}

Use any C library - right now

You don't have to wait for the ecosystem to catch up. The extern "C" from library block declares the C ABI you want to call into, and the linker does the rest. Wrap the opaque handle in a thin type that implements Disposable and the cleanup call disappears from your code - the disposable kind emits it at scope end. 

// Pull SDL2 in directly - no bindings crate, no shim, no rewrite.
extern "C" from library "SDL2" {
    type SDL_Window;
    type SDL_Renderer;

    function SDL_Init(flags: uint32): int32;
    function SDL_Quit(): void;
    function SDL_CreateWindow(
        title: string,
        x: int32, y: int32, w: int32, h: int32,
        flags: uint32
    ): ref SDL_Window;
    function SDL_DestroyWindow(ref win: SDL_Window): void;
    function SDL_RenderPresent(ref ren: SDL_Renderer): void;
}

// Thin yoop wrapper so the `disposable` kind manages the handle.
// No manual SDL_DestroyWindow at the bottom of main().
type Window implements Disposable {
    handle: ref SDL_Window,
    function dispose(ref self): void {
        SDL_DestroyWindow(self.handle);
    }
}

const SDL_INIT_VIDEO: uint32 = 0x00000020;
const SDL_WINDOW_SHOWN: uint32 = 0x00000004;

function main(): int32 {
    if (SDL_Init(SDL_INIT_VIDEO) != 0) { return 1; }

    disposable win: Window = {
        handle: SDL_CreateWindow("hello", 0, 0, 800, 600, SDL_WINDOW_SHOWN)
    };

    // ... render loop here ...

    SDL_Quit();
    return 0;  // win.dispose() fires here, automatically.
}

The point: you can start writing real programs today by reaching into anything C already exposes - graphics, audio, databases, crypto. The Yooperlang-native ecosystem grows over time; the C ABI is the bridge in the meantime.
