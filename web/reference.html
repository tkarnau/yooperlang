Overview

Yooperlang (.yoop) is a systems language with a TypeScript feel: no garbage collector, no classes, structs plus free functions, types on the right, and every behavioral contract expressed through two orthogonal mechanisms, traits and kinds. Source compiles to LLVM IR text, and the compiler shells out to clang to link a native executable.

LayerRoleAttached toExamples
Type What the value is: the concrete data shape Variables, fields int32, Point, Vec<T>
Trait What the value can do: operations it supports Types Disposable, Display, Iterable<T>
Kind How the binding must be used: lifecycle, scoping, sharing Bindings, parameters, fields, functions, regions disposable, ephemeral, task, pooled

That separation is what makes async unnecessary as a piece of API vocabulary, makes cleanup declarative, and lets a test framework be a library rather than a language feature. A kind can require a trait (the value must support certain operations) and can make the compiler inject code at the binding site.

Modules and imports

Every .yoop file is a module. Imports are relative paths by default; the std/ prefix resolves against the bundled standard library, and modules/ against the program's own module folder. Imports come first in a file, before any declaration. 

import { parse, lex } from "./lexer.yoop";
import * as lex        from "./lexer.yoop";
import { parse as p }  from "./ast.yoop";
import "./init.yoop";                     // side effect only

import * as math from "modules/math";     // a module the program installed

import { Vec } from "std/core/vec.yoop";  // types by name
import * as vec from "std/core/vec.yoop"; // values need the namespace

// Both axes on one line, either ordering.
import * as vec, { Vec } from "std/core/vec.yoop";

Std values must be namespaced

A named import of a function or const from any std/ path is a hard error. Short names like info, error or vecNew would otherwise shadow user identifiers in every module that touched the library. Types, traits, kinds, variants and enums are exempt, because their capitalization or syntactic position separates them from value identifiers. 

import { info, error } from "std/log.yoop";   // rejected
import * as log from "std/log.yoop";           // correct: log.info(...)

Directory modules

A module is a single file, or a directory of files that each declare module <name>; as their first line. Inside a directory module, declarations are shared but imports are not: siblings see each other's declarations whether exported or not, which is how a module gets real privacy, but using a name that only a sibling imported is an error. Import the module, never one of its files: from "std/http", not from "std/http/server.yoop".

The modules/ root

modules/<name> resolves against the nearest modules directory at or above the importing file. Three rules follow from anchoring on the importer rather than the entry point: a module reaches its own dependencies through the same root, dependencies are flat with one copy of a name per program, and a module under development uses the same import line it will ship with. There is no manifest, no fetch and no version resolution. The directories are put there by hand.

Per-file flags

import.unsafe; enables unsafe_ptr<T> in that file, and import.test; declares that the file is a test module with no main on purpose. Both are per source file, not per module, which is what lets one file in a directory module name unsafe_ptr while its siblings may not.

Primitives and literals

GroupTypesNotes
Signed int8 int16 int32 int64 isize int is an alias for int32
Unsigned uint8 uint16 uint32 uint64 usize uintptr uint8 is the canonical byte; usize is every length and index
Float float32 float64 float is an alias for float32
Other bool char string void string is an immutable, nul-terminated, borrowed UTF-8 view

Literals are untyped until they land

An integer or float literal has no type until it reaches a typed context, where it is range-checked and pinned. There is no implicit widening or narrowing between named numeric types, in either direction. This is the rule that surprises people first and stops surprising them within a day. 

let hp: int32   = 100;
let mask: uint8 = 0xFF;
let big: uint64 = 1_000_000_000;
let dt: float32 = 1.0 / 60.0;

let a: int32 = 10;
let b: int64 = a;              // compile error: explicit cast required
let c: int64 = int64(a);       // ok - casts spell the type as a call

let over: uint8 = 256;         // compile error at parse time: out of range

Literal forms: decimal (1_000_000), hex (0xDEAD_BEEF), binary (0b1111_0000), octal (0o755), float (6.022e23). Narrowing casts truncate, same-width signed and unsigned casts reinterpret bits, and float to int truncates toward zero.

Char literals own the single quote

Strings use double quotes, templates use backticks, and the single quote is reserved exclusively for a one-scalar char literal. A char literal evaluates to its codepoint and is untyped exactly like an integer literal, which is what lets byte-oriented code read as ch == '\n' instead of ch == 10.

Template literals

Backtick strings interpolate with ${expr}, the same idea as JavaScript. Interpolation is a Display trait lookup, not a hardcoded list of printable types, so your own type becomes interpolatable by implementing the trait (or by adding @derive(display) above it).

Types

Structs

Plain data. No methods inside a bare type, no inheritance, all fields public. Types are nominal: two structs with identical fields are two different types. 

type Point {
  x: int32,
  y: int32,
}

// A struct literal has no type of its own, so it needs a target: an
// annotated binding, a return type, or a parameter type.
let p: Point = { x: 1, y: 2 };

Variants, enums, unions

variant is the tagged union: a value is exactly one of the listed cases, cases may carry payloads, and switch must be exhaustive. enum is the C-style value enum of named constants. union is genuinely untagged with C layout, for FFI, with no safety by design. 

variant Shape {
  Dot,
  Circle { r: int32 },
  Rect { w: int32, h: int32 },
}

enum Color { Red, Green, Blue }

union Pixel {
  rgba: uint32,
  channels: Channels,
}

function area(s: Shape): int32 {
  switch (s) {
    case Shape.Dot: { return 0; }
    case Shape.Circle { r: r }: { return 3 * r * r; }
    case Shape.Rect { w: w, h: h }: { return w * h; }
  }
}
why exhaustiveness is the point

Add a case to a variant a year from now and the compiler walks you to every switch in the program that needs a new arm. That refactor is most of the value; the destructuring syntax is just how you spend it.

Type aliases

type Name = <type>; (note the = and the trailing semicolon) introduces a transparent alias with no identity of its own. A NodeId is a usize everywhere, so an alias documents intent but will not stop you passing a raw usize.

Arrays and slices

Arrays are fat pointers, pointer plus length, and the length is intrinsic as xs.len (a usize). Slicing with xs[i..j] produces a borrowing view with no copy and no allocation. 

let xs: int32[] = [1, 2, 3];
let n: usize = xs.len;
let mid: int32[] = xs[1..3];      // a view, not a copy

References

ref T is visible at formation and at passing, and transparent at use. No null, no arithmetic. The escape hatch for C-style pointers is unsafe_ptr<T>, which is a distinct type and is gated behind import.unsafe;.

There is no null

Absence is modeled explicitly: Option<T> from std/core/types.yoop, a variant case of your own, or a validity field. A missing map entry comes back as Option.None, not as a sentinel you have to remember to check.

Bindings

let x: int32;                  // zero-initialized
let y: int32 = 3;              // mutable
const z: int32 = 42;           // immutable binding

disposable f: FileHandle = open("x.txt");   // kind prefix, implicitly const
let disposable g: Text = text.make(64);      // explicit let for mutability

A kind prefix sits between let / const and the name, and lets you drop the let / const keyword entirely. Such a binding is implicitly const, and that is not symmetry for its own sake: the injected cleanup fires once, at scope end, on whatever the binding holds then, so rebinding would silently drop the outgoing value without disposing it. Writing let is the informed opt-in, and it comes with the obligation to dispose the old value before overwriting.

Block-owning kinds

A kind that declares ownsBlock may take a trailing { ... } that narrows the binding's scope. Leave the block off and the compiler synthesizes one at the tail of the enclosing scope; multiple such bindings nest in reverse declaration order, so cleanup is LIFO. 

// Explicit: the lifetime is lexically visible.
disposable input: Input = openInput(path)? "opening input" {
  const bytes = readAll(ref input)? "reading bytes";
  return Result.Ok { value: scan(bytes)? };
  // dispose(input) fires at the closing brace, including on the `?` paths
}

// Implicit: same cleanup, scope is the rest of the enclosing scope.
function analyze(path: string): Result<Report, string> {
  disposable input: Input = openInput(path)?;
  const bytes = readAll(ref input)?;
  return Result.Ok { value: scan(bytes)? };
}

Region kinds: an owner with no name

A kind declaring appliesTo region governs a lexical region rather than a named value. It is the right shape when the value exists only for the ambient state it installs on entry and undoes on exit: an allocator scope, a pushed context, a transaction, an indent level. It is used with no binding name at all. 

ephemeral mem.allocatorScope(arena) {
  const t: Text = text.fromString("comes out of the arena");
}                                    // teardown fires at the brace

ephemeral mem.allocatorScope(arena); // no block: teardown at enclosing scope end

The two shapes are mutually exclusive and the compiler enforces the distinction in both directions: an appliesTo binding kind used without a name is an error telling you to name it, and an appliesTo region kind given a name is an error telling you to drop it. There is no defer, no using and no with statement; these are two spellings that fall out of one clause.

Destructuring

Surface sugar only. const { value, err } = call(); is rewritten into a temporary plus field reads, so there is no multiple-return ABI anywhere in the language.

Traits

A trait is a set of operations a type must provide. Traits never carry state, self is always a ref, and extends chains them. 

trait Disposable {
  function dispose(ref self): void;
}

trait Iterable<T> {
  function next(ref self): IterStep<T>;
}

type FileHandle implements Disposable {
  fd: int32,
  function dispose(ref self): void {
    closeFd(self.fd);
  }
}

// More than one trait is parenthesized.
type Channel implements (Disposable, Iterable<Message>) {
  // fields, then method bodies
}

Calls are trait-qualified

Disposable.dispose(ref x). Not x.dispose(), and not a bare dispose(ref x); both are rejected with a fix-it. The trait name at the call site is what lets a trait method name freely coincide with a module-level free function, or with a method from another trait the same type implements, with no ambiguity and no resolution order to learn.

known gap

Two traits declaring the same method name, implemented by one type with two different bodies, is not expressible. One body satisfies both.

Vtables: runtime trait dispatch

Generics give compile-time trait polymorphism, which is the right answer for performance but makes heterogeneous collections impossible: a T[] holds one monomorphization at a time. A vtable declares the runtime-polymorphic shape backing a trait, a struct of a context pointer plus one function pointer per method. 

trait Readable {
  function read(ref self, ref buf: uint8[]): int32;
}

vtable Reader for Readable {
  read: (ref buf: uint8[]) => int32,
}

const r: Reader = Reader.from(ref myTcpStream);   // from any implementor
const n = Reader.read(ref r, ref buf);            // indirect dispatch

VTableName.from(ref x) builds one from any ref T where T implements the trait. VTableName.fromFn(f1, f2, ...) builds one from named functions with no struct or impl at all, in trait declaration order. Both produce the same nominal type, so one array can hold a mix.

Function values

(p: T) => R is a function-value type annotation, legal in struct fields, parameters, return types and vtable fields. It is only a type annotation: => is not closure syntax, and closures are not planned. A bare top-level function name materializes to a plain code pointer wherever a matching type is expected, capturing nothing. Wrap the whole function type in parentheses to hang an array suffix off it: ((ch: uint8) => bool)[].

Kinds

A kind is a usage-site contract. It attaches to bindings, parameters, fields, functions or regions and encodes lifecycle, scoping, sharing, concurrency mode or propagation. Kinds are the single mechanism for "the compiler should enforce X here", and nothing about them is reserved to the standard library. 

export kind disposable {
  appliesTo binding;
  requires Disposable;
  mustCall dispose beforeScopeEnd;
  ownsBlock;
}

export kind task {
  appliesTo function;
  pausable;                 // the function is a coroutine
  provides Task;            // the CALL SITE yields Task<ReturnType>
}

export kind pooled {
  appliesTo binding parameter field;
  requires Shared;
  refcounted retain release;
}

Every clause is a semicolon-terminated statement. No parens, no method chains, no colons: clause types are a closed set the compiler owns, and the grammar reflects that. Multiple requires are separate clauses rather than a list.

What a kind can declare

ClauseMeaning
appliesTo X...One or more of binding, parameter, field, function, type, return, or the standalone region.
requires TraitValues of this kind must implement the named trait. Repeat for more.
provides NameRewrites the call-site result type of a function carrying the kind: the body returns T, the call evaluates to Name<T>. Resolves only to Task today.
pausableFunctions carrying the kind are coroutines, which forces the await calling convention.
refcounted retain releaseNames the two methods the compiler calls to bump and drop a reference. Dispatched for a Task<T> receiver.
ownsBlockThe binding may take a trailing block that narrows its scope; without one the compiler synthesizes it at the tail of the enclosing scope, LIFO.
mustCall fn beforeScopeEndThe named method must run before the binding's scope exits. If you already called it by hand on every path, no second call is injected.
mustNotEscape scopeCannot be returned or stored outside its scope. Enforced, and also what lets the compiler keep the binding in a stack slot.
mustNotShare acrossThreadsCannot flow into a task spawn. Rejected statically at every task-call argument site.
conferred / restrictiveMakes this a marker kind: a static tag with no obligation and no codegen. See below.
clearedBy m / appliedBy mNames the trait method authorized to strip (restrictive) or grant (conferred) the marker.
signature (p: T) => RThe shape every function carrying this kind must have. Required on a collected function kind.
enumerable as "table"Names the table a consumer asks the compiler for. This is the entire compiler contribution to the test harness.

propagates<K>Documents that values of the type own a resource. Advisory: see below.

restricts iteration, contains<K>, mustCall ... beforeAnyReserved; rejected with a "not yet supported" error.

Behavior comes from the clause, not the name

The compiler reads clauses off whatever kind declaration it finds, so a kind you write gets exactly the treatment the standard library's does. This is worth stating plainly because the concurrency kinds look built in and are not: task, async, joined and pooled are ordinary declarations in std/core/kinds.yoop, and they lex as ordinary identifiers. 

kind spawn {
  appliesTo function;
  pausable;
  provides Task;
}

spawn work(): int32 { return 7; }

function main(): int32 {
  pooled h = work();          // h is Task<int32>
  printf(`v=${wait h}\n`);
  return 0;
}

Three things are genuinely the compiler's and cannot be spelled by a user kind: Task<T> itself, refcounted on a non-Task receiver, and the set of names provides can resolve to. Because the compiler consults these clauses rather than the names, the standard library's declaration is load-bearing, and the compiler checks it: delete provides Task from task and every program that spawns stops building, with an error naming the missing clause.

Ownership is advisory; auto-cleanup is the opt-in with teeth

propagates<K> on a type documents that bindings of it own a resource. It does not force the user to do anything, and there are no unsatisfied-obligation errors. Writing the kind keyword on the binding is the opt-in that has teeth: the compiler injects the cleanup at scope end. An earlier version of this language made unhandled resources a hard error, and it was miserable to use.

never return a disposable binding

This is the easiest way to write a silently broken program, because the broken version looks correct and the compiler says nothing. disposable means "clean this up when this scope ends", so a value you hand back has already been freed by the time the caller sees it. 

// WRONG. Compiles clean, runs, hands back freed storage.
function build(n: usize): Result<Text, string> {
  disposable out: Text = text.make(n);
  return Result.Ok { value: out };
}

// RIGHT. Plain `let`, and the signature documents the transfer.
function build(n: usize): Result<Text, string> propagates<disposable> {
  let out: Text = text.make(n);
  return Result.Ok { value: out };
}

Marker kinds and typestate

A marker kind generates nothing at all: no runtime cost, nothing in the binary. It exists only to make certain programs fail to compile. restrictive is a hazard that a plain slot forbids, so it cannot be silently dropped. conferred is a capability that a slot naming it requires, so it cannot be forged.

The part that makes this more than type-shuffling: a transition must go through the trait method the kind names via clearedBy or appliedBy. A free function with exactly the right shape is not authorized to launder a marker. That is the difference between "the types line up" and "someone authorized this", and it means laundering is a visible, greppable act.

Composition

kind slowBatch = throughputCapped(8) & mustNotEscapeKind;
kind scopedAlt  = disposableBase & { mustNotEscape scope; };

An inline body is an anonymous bag of clauses, useful for tacking one restriction onto a composition. It may contain any clause except appliesTo, since the composition's application sites are the intersection of its named operands. Contradictory compositions are compile errors, and so is a composition whose operands share no application site.

Generics

Type parameters on functions and types, bounds spelled with the same implements word structs use. Generics monomorphize: one real machine function per concrete type you call with, no boxing, no runtime dispatch. Bounds are checked at the call against the concrete type. 

function identity<T>(x: T): T {
  return x;
}

function describe<T implements Display>(ref x: T): void {
  printf(`[${Display.toString(ref x)}]\n`);
}

function pairUp<A implements (Display, Copyable), B>(a: A, b: B): void { }

type Box<T> {
  value: T,
}

Type arguments at call sites are always inferred from the arguments. There is no turbofish, so < in expression position stays less-than. One consequence worth knowing in advance: an untyped literal does not pin against a type parameter, so identity(42) cannot infer T. Deliberate, and arguable: otherwise the literal defaulting rule would be silently choosing your instantiation.

known limitation

Call-site inference cannot see through a generic variant's type arguments, so function bridge<T>(r: Result<T, string>) will not infer T from a Result<int32, string> argument, and there is no turbofish to say it out loud. The workaround is one small bridging helper per payload type.

Functions

function add(a: int32, b: int32): int32 {
  return a + b;
}

// A kind prefix makes the `function` keyword optional.
task fetch(url: string): Bytes { }
async double(x: int32): int32 { return x * 2; }
task disposable openRemote(url: string): RemoteHandle { }

// `ref` is written at BOTH ends, so aliasing is visible at the call site.
function increment(ref counter: int32): void {
  counter = counter + 1;
}

let n: int32 = 0;
increment(ref n);

There are no nested functions and no closures: declare at module scope. Methods live inside type ... implements Trait { ... } blocks; there is no bare impl block, and a method always implements a trait.

Control flow

if (cond) { } else if (other) { } else { }

while (cond) { }

for (let i = 0; i < n; i += 1) { }   // counter scoped to the loop
for i in 0..xs.len { }                // a range value
for x in xs { }                       // an array
for x in vec.vecIter(ref v) { }       // anything Iterable<T>

switch (value) {
  case Shape.Circle { r: r }: { }
  case Shape.Dot: { }
}

break;  continue;  return;  return expr;

The counted loop takes its type from the condition

When a for-head counter has no annotation and its initializer is a bare numeric literal, the type comes from the loop condition: comparing against xs.len gives you a usize, not the int32 a plain let i = 0 would infer. It is the one place in the language where context overrides a literal's default, and it exists because otherwise the most ordinary loop you can write would fail on its own condition.

Ranges

a..b is a half-open integer range yielding usize, which is why 0..xs.len needs no casts. It is sugar for a call into std/core/range.yoop, so a range is an ordinary value implementing Iterable<usize>: bind it, pass it, walk it more than once. Bounds cannot be chained, and inside brackets .. keeps its slice meaning.

Every path must return

A function whose return type is not void must return on every path, and the rule is divergence, not "the last statement is a return". return, break and continue all diverge; an if diverges only with an else where both arms do; an exhaustive switch whose arms all diverge does, which is why an arm-per-case switch needs no trailing return; while (true) with no reachable break does, and no other loop does, because its condition may be false on entry.

Errors as values

There are no exceptions. A fallible type is a variant with exactly two cases named Ok and Err, each carrying at most one payload field. The shape is structural, with no marker trait, so any variant of yours participates. Result<T, E> in std/core/types.yoop is an ordinary declaration, not a built-in. 

export variant Result<T, E> {
  Ok { value: T },
  Err { error: E },
}

export variant Option<T> {
  Some { value: T },
  None,
}

The three forms of ?

const bytes = readAll(path)?;                 // propagate Err unchanged
const line  = readLine(buf)? "reading head";  // prepend context
const db    = sqlite.open(path)? e {          // handle it here instead
  return Result.Err { error: httpError(status(500), e) };
};

Bare ? only compiles inside a function that itself returns a fallible shape, which is what keeps a chain from quietly ending. To stop propagating you have to say what happens, so the place the buck stops is visible in the source.

The handler form drops that requirement entirely, because nothing is being propagated: it is legal in main, in a method returning a plain value, anywhere. Its one rule is that the block must diverge on every path, since it runs instead of producing a value. return, break and continue all count, which is what makes const v = step(ref st)? e { continue; }; legal inside a loop.

Context strings are lazy

? "msg" and ? `msg ${n}` attach a context message, and the expression is evaluated only on the failure branch, so an interpolated template costs nothing when the call succeeds. For a string payload the compiler concatenates "context: err" itself and contexts stack as the error travels outward. For a structured payload the type implements WithContext<T>, and the impl decides where the context goes, which is how a line field survives untouched.

Crossing error types

When the operand's Err payload type differs from the enclosing function's, the operand type implements Into<TargetErr> and the compiler inserts the conversion on the failure branch. WithContext<T> subsumes Into<T>, so one impl covers both when a context is attached. A string payload can carry neither impl, since a primitive has no implements list, and that is exactly what the handler form is for.

Concurrency

Concurrency is a kind story. task applied to a function means every call is semantically a spawn, and the call site evaluates to Task<T>. The binding's kind decides when the wait happens.

BindingWhen the wait happensStorage
const a = f();Immediately: the next statement sees the value.Stack handle, spawn plus wait inline.
joined d = f();At the enclosing scope's closing brace, or at the first read if earlier.Stack, bounded by scope.
pooled h = f();Never automatically. You call wait h.Heap, atomically refcounted.
 
task compute(x: int32): int32 {
  return x * x;
}

function main(): int32 {
  const a: int32 = compute(3);      // synchronous-looking
  joined d = compute(4);            // concurrent, joined at the brace
  pooled h = compute(5);            // a handle you wait on yourself
  printf(`${a} ${wait d} ${wait h}\n`);
  _ = compute(6);                    // fire and forget: the result is dropped
  return 0;
}

async and await

async is a real color and the rules are enforced. An async function lowers to an LLVM coroutine, await is the only way to call one, and await is only legal inside another async function or a task body (which is implicitly async). Those two rules together guarantee a suspend always has a frame to propagate into.

wait blocks a thread; awaitTask suspends a task

Inside a task body only conc.awaitTask(h) is legal, and wait is rejected outright. "Await all" is an ordinary loop over awaitTask: each iteration frees the worker, and completion order does not change the answer. The sync-to-async bridge at the top of a program is main spawning a task and waiting on it.

Bounded waits and cancellation

waitUntil(h, deadlineNs) returns a WaitResult<T>: Done with the value, Timeout, or Cancelled. The deadline is absolute, in the same clock space as nowNs(). cancel(h) sets the handle's cancel flag and wakes anything parked on it; the body itself is not cooperative, so it runs to natural completion while the caller has simply stopped observing.

Strings, text, and memory

This is where the language has moved most, and where old examples mislead most often. The split is ownership.

stringText
What it isA borrowed view: a nul-terminated char *An owned, growable buffer
AllocationRaw malloc, ignores the allocator contextRoutes through the ambient allocator, and captures it
CleanupNothing frees itdisposable, so cleanup is injected
.lenA strlen call, O(n) every timeTracked
Use it forAnything that only readsAnything that builds or accumulates
a string you BUILD leaks

Every template literal is a fresh malloc. So is every stringConcat, padStart, intToString. disposable on a Vec<string> frees the vector, never the strings in it, and --track-heap cannot even see any of it. Anything accumulating text in a loop takes a Text. 

// leaks one string per line, plus one per interpolated number
disposable lines: Vec<string> = vec.vecNew(64);
vec.vecPush(ref lines, `  ret i32 ${value}\n`);

// leaks nothing, and an enclosing arena reclaims it
disposable out: Text = text.make(1024);
text.push(ref out, "  ret i32 ");
text.pushUint(ref out, value);      // formats digits straight into the buffer
text.pushByte(ref out, '\n');

Measured rather than theoretical: moving the bootstrap compiler's IR emitter from the first shape to the second took one compile from 3266 leaks and 244KB to 632 leaks and 131KB, with no behavior change.

One more edge worth knowing before it bites: arguments are eager, so an assert or log message with an interpolated template allocates on every call, passing or not. Guard the hot ones with an if. And string == string does not compile; use text.equals or str.stringEq.

Allocators and arenas

The current allocator is ambient and held per thread, or per task inside a task. Two canonical scoped forms: install an existing arena for a region, or make a new arena that is the region. 

// (a) install an existing arena; anonymous, nothing to name
ephemeral mem.allocatorScope(ar) {
  let t: Text = text.fromString("comes out of ar");
}

// (b) make a new arena, name it, tear it down at the brace
disposable reg: mem.ArenaScope = mem.arenaScope(4096) {
  let p: unsafe_ptr<void> = mem.allocBytes(64, 8);
}

Vec<T> and Text are container-owned: each captures the allocator current when it was built and routes every later grow and the final free back through that same one. Scratch space is mem.tempAllocator() plus one mem.resetTemp() at a boundary; it belongs to the task when you are inside one, so a task's scratch is invisible to every other task.

allocation failure is not checked

An exhausted arena or a failed malloc returns null and you dereference it. There is no diagnostic. Size arenas generously.

C interop

extern "C" from "stdio.h" {
  function printf(fmt: string, ...): int32;
  function fopen(path: string, mode: string): ref FILE;
  type FILE;
}

extern "C" from library "m" {
  function cos(x: float64): float64;
}

export "C" function onTick(ms: int32): int32 { return ms + 1; }

from library "NAME" emits a -lNAME to the linker. export "C" emits an unmangled symbol with the C ABI. Extern blocks keep the real C symbol names, underscores and all, because those are link-level names rather than style choices; a struct mirroring a C ABI struct keeps the C field spellings for the same reason.

Unsafe pointers

Gated per file behind import.unsafe;. unsafe_ptr<T> is a distinct type, not a kind on ref T. 

import.unsafe;

let q: unsafe_ptr<int32> = &x;      // address-of an lvalue
let v: int32 = *q;                    // deref read
*q = 42;                              // deref write
let r = q + 1;                        // strides by sizeof(int32)
let n: int64 = r - q;                 // element count
let isNull: bool = (q == null);

let bp = unsafe_ptr.cast<uint8>(q);
let as_int: uintptr = unsafe_ptr.toInt(q);

Two bridges connect fat-pointer arrays to raw buffers: xs.ptr borrows the data pointer of any array, and unsafe_ptr.toArray<T>(p, n) wraps a pointer and length as a borrowing T[] view with no copy. Pointers do not participate in kind containment, and they are rejected inside pure functions.

Portable integer aliases and errno

c_int, c_long, c_size_t and friends are typecheck-time synonyms for fixed-width Yoop integers under LP64. Using one in an extern signature documents portability intent. errno.get(), errno.set(v) and errno.message(code) are thread-local intrinsics; the recommended pattern is a Yoop-side wrapper that converts a -1 plus errno into a Result.

Raw memory

heapAlloc<T>(n) and heapFree<T>(a) are compiler-recognized generics in std/core/intrinsics.yoop: malloc and free, with the result presented as a fat-pointer T[]. Typical use is through a Disposable wrapper such as Vec<T> rather than directly. ctxAlloc and ctxFree are the allocator-context-routed siblings.

Testing

Testing has no compiler-baked semantics. test, suite and the assertion helpers are ordinary kinds and functions in std/test.yoop, and all three remain usable as identifiers. A test module is a *.test.yoop file declaring import.test; first and having no main. 

import.test;
import * as t from "std/test.yoop";
import { suite, test, Case } from "std/test.yoop";
import { strangeAdd } from "./strange_add.yoop";

suite function addsStrangelyWhenFirstIsTwoModFive(): void {
  let test theory: Case = t.asserts("adds an extra 1 when a % 5 == 2") {
    const got = strangeAdd(2, 2);
    theory.isSuccessful = got == 5;
    theory.detail = `strangeAdd(2, 2) gave ${got}, wanted 5`;
  }
}

An assertion is a bool plus a string, deliberately not a comparison: two operands flatten the context that made the check meaningful, and detail is reported only on failure. Run with yoopiler_boot --test <dir>, optionally with filters as extra positionals. Suites are the unit of isolation, each running inside an arena scope; cases are the unit of reporting; the exit code is the failure count.

Naming and keywords

Identifiers are [A-Za-z_][A-Za-z0-9_]*. The conventions are enforced by convention, not by the compiler, but the whole standard library follows them.

ThingConventionExamples
Files and directoriessnake_casescan_tables.yoop, source_graph/
Types, traits, variants, vtables, type params, case namesPascalCaseResult.Ok, Display
Functions, methods, locals, params, fields, kind namescamelCasevec.vecNew, Display.toString
Value-enum cases and module-level constsSCREAMING_SNAKETokenTags.EOF, SEEK_SET

snake_case is never used for an identifier, with two carve-outs that are really one rule (mirror the C side exactly so a reader can match it against a header): extern "C" symbol names, and structs mirroring a C ABI struct.

Many words that read like keywords are contextual and remain legal identifiers: module, test, suite, signature, enumerable, conferred, clearedBy, plus the clause words in, layout, provides, requires, appliesTo, ownsBlock, mustCall, from, library, as. Every kind name is an ordinary identifier too, which is exactly why a test framework can be a library.

Not here on purpose

  • Classes, inheritance, methods on bare types. Traits plus free functions only.
  • Garbage collection. Lifetimes through mustCall, mustNotEscape and dispose.
  • Implicit conversions. Explicit casts only, in both directions.
  • Exceptions. Every error boundary is visible at the token level: a ? or an explicit switch.
  • Closures. A function value is a plain code pointer that captures nothing.
  • A multiple-return ABI. Destructuring is compile-time sugar over a returned struct.
  • A package manager. Relative paths, the std/ root, and a program-owned modules/ root that you populate by hand.
  • A borrow checker. The trade is explicit and it is the central bet of the language.

The full grammar, including the reserved-word list and the parts still marked reserved, is in SPEC.md. Current practice, including the sharp edges, is in docs/writing_yoop.md.
