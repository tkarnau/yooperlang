# Yooperlang - Claude working notes

A JS-implemented compiler for the Yooperlang language. Emits LLVM IR text, shells out to `clang` to link and produce an executable. Language spec in [SPEC.md](SPEC.md). Phases 1 through 9 plus library phases A–D have landed (per-phase docs in [plans/completed/](plans/completed/)); the full historical roadmap is at [plans/archive/roadmap.md](plans/archive/roadmap.md). **The current focus is the self-hosting bootstrap** - rewriting the JS compiler in Yoop, layer by layer, cross-checked against the JS reference. [plans/README.md](plans/README.md) is the single source of truth for what is being worked on now; the long-tail Phase 10 items live in [plans/archive/phase-10.md](plans/archive/phase-10.md).

Pipeline: source `.yoop` → **lex** → **parse** → **typecheck** → **codegen** (LLVM IR) → `clang` → executable.

## Naming and file conventions

The repo currently has a mixture; this is the go-forward convention. Follow it in
new code. Existing non-conforming names are being renamed retroactively (do not
block on them, but do not add more).

- **Files and folders: `snake_case`** - repo-wide, both `.yoop` and `.js`. e.g.
  `source_processing/`, `module_graph.yoop`, `array_utils.yoop`.
- **Yooperlang (`.yoop`) identifiers** use one of three cases - never
  `snake_case` (reserved for files/folders; the underscore is still legal in the
  grammar but convention does not use it in identifiers):
  - **`PascalCase`**: types and type-like decls - struct / `type`, `trait`,
    `variant`, `enum`, `union`, `vtable`, type parameters - and `variant` case
    names (`Result.Ok`, `Option.None`).
  - **`camelCase`**: functions, methods, local bindings (`let` / `const`),
    parameters, struct fields, and kind names (`disposable`, `nulTerminated`).
  - **`SCREAMING_SNAKE`**: value-`enum` case names (`TokenTags.EOF`,
    `ASTNodeKind.FUNCTION_DECL`) and module-level `const` declarations
    (`SEEK_SET`, `TOKEN_SCAN_LIST`). (Note: `const` is overloaded - a top-level
    constant is `SCREAMING_SNAKE`; a local `const` binding is `camelCase`.)
- **The JS reference impl** uses ordinary JS identifier conventions (camelCase
  functions, etc.); only the file/folder `snake_case` rule applies to it.
- **Known legacy to migrate retroactively** (target in parentheses):
  - std functions are `snake_case` (`vec_new`, `read_file`, `map_get`) ->
    `camelCase` (`vecNew`, `readFile`, `mapGet`).
  - some module-level consts are `camelCase` (`tokenScanList`, `keywordList`) ->
    `SCREAMING_SNAKE` (`TOKEN_SCAN_LIST`, `KEYWORD_LIST`).
  - JS reference-impl filenames / dirs are camelCase (`jsyooplexer/`,
    `kindCheck.js`) -> `snake_case`.

## Run / test

- `npm test` - all tests (unit + e2e)
- `npm run test:unit` - fast, no clang
- `npm run test:e2e` - full pipeline, requires `clang` on PATH
- Driver entry: [src/yoopiler.js](src/yoopiler.js). End-user invocation is `yoopiler <entry.yoop>`; the entry file pulls in everything else via its imports.

## Subsystem map

### [src/jsyooplexer/](src/jsyooplexer/) - lexing (~630 lines)
- Public entry: `tokenize(src) → Token[]` at [lexer.js:406](src/jsyooplexer/lexer.js#L406). Throws on first lex error.
- Single-token form: `lexNext(src, pos)` at [lexer.js:334](src/jsyooplexer/lexer.js#L334).
- Token shape: `{ tag, start, length, intVal?, floatVal? }`. `start`+`length` are character offsets into `src` - extract text via `src.substring(start, start + length)`.
- `TokenTags` enum and `keywordTagList` map live in [lexer.js](src/jsyooplexer/lexer.js). Character predicates in [charFns.js](src/jsyooplexer/charFns.js); whitespace + nestable block comments in [charEaters.js](src/jsyooplexer/charEaters.js).
- Numeric literals support underscore separators (validated: must be between digits) and `0x`/`0b`/`0o` bases. Block comments nest. Template literals (backticks) are returned raw; `${...}` interpolation is parsed later in the parser.
- **Quote ownership**: double quote = `strLiteral`, backtick = `templateLiteral`, single quote = `charLiteral` (exclusively - there are no single-quoted strings). `lexCharLiteral` decodes one Unicode scalar (escapes `\n \r \t \0 \\ \' \"` and `\xNN`, plus astral scalars via `codePointAt`) into the token's `intVal`; empty/multi-char/bad-escape are lex errors. The parser lowers a `charLiteral` token to an `INT_LITERAL` node carrying the codepoint, so a char literal *is* an untyped int downstream - it pins to any integer type and range-checks like a numeric literal (`ch == '/'` against a `uint8`). No `char` type or AST node exists yet; `char` in [types.js](src/jsyooptypecheck/types.js) is a name placeholder, not wired into coercion.

### [src/jsyooparser/](src/jsyooparser/) - parsing (~2,000 lines)
- Public entry: `parse(src) → ASTNode` (PROGRAM root) at [parser.js:79](src/jsyooparser/parser.js#L79). Throws via `parseError` with line/column/caret; one error aborts the whole parse.
- Recursive descent with Pratt-style precedence climbing for binary ops. Precedence table at [parser.js:52](src/jsyooparser/parser.js#L52); climbing loop in `parseExpression(minPrecedence)`.
- Parser state (`pos`, `current`) is closure-scoped inside `parse()`. No resumability. Helpers: `advance`, `peek`, `peekAhead(n)` (re-lexes, no cache - keep lookahead shallow; existing max is 3 tokens for kind-prefixed bindings).
- Every node is created via `buildSourcedNode(ASTNodeKind.X)` at [parser.js:218](src/jsyooparser/parser.js#L218) so `sourceLoc` is set - downstream error reporting depends on this.
- Deferred-feature pattern: keywords reserved for later phases (e.g. `provides`, `restricts`) lex as plain identifiers and the parser emits an explicit "not yet supported" message if they appear in a clause. Mirror this when reserving anything new.
- **Generics (Phase 7.1)**: `parseTypeParamList()` parses `<T, U>` after a decl name and wires `typeParams` onto `FUNCTION_DECL`/`TYPE_DECL`/`TRAIT_DECL`. `parseTypeAnnotation()` accepts a type-application shape - any identifier followed by `<` becomes `{ name, typeArgs: [TypeAnnotation] }`. `>>` is split into two `gt` tokens parser-side when closing a nested type-application so `Pair<int32, Box<int32>>` parses; the lexer is unchanged. Explicit type args at call sites are not supported - `<` in expression position is still a binary op, keeping `peekAhead` shallow.

### [src/jsyooptypecheck/](src/jsyooptypecheck/) - type system (~6,400 lines across ~13 files)
- Orchestration in [typecheck.js](src/jsyooptypecheck/typecheck.js) - passes A (declarations), B (signatures), C (bodies + kind resolution).
- Types in [types.js](src/jsyooptypecheck/types.js): `PrimType`, `StructType`, `RefType`, `ArrayType`, `FuncType`, `KindType`, `KindApplication`, `TaskType`, `TraitType`, `TypeParamType`. Also `untypedInt`/`untypedFloat` literal placeholders and `error`/`namespace`.
- Per-node dispatchers (recursive on `node.kind`, not visitor): expressions in [checkExpr.js](src/jsyooptypecheck/checkExpr.js) (`resolveExprType`, `checkInitializer`); statements + function bodies in [checkStatement.js](src/jsyooptypecheck/checkStatement.js).
- Kind flow analysis (mustCall obligations, escape analysis, propagation) in [kindCheck.js](src/jsyooptypecheck/kindCheck.js).
- Coercion rules in [coerce.js](src/jsyooptypecheck/coerce.js) (`isAssignable`, `unifyArith`, literal pinning). Lexical scope chain in [scope.js](src/jsyooptypecheck/scope.js). Errors accumulated via `pushError` in [errors.js](src/jsyooptypecheck/errors.js) (not thrown). Fallible (`err`-bearing) binding tracking in [fallible.js](src/jsyooptypecheck/fallible.js). Builtin kinds (`joined`, `pooled`, `Task`) in [builtinKinds.js](src/jsyooptypecheck/builtinKinds.js). Cross-module symbol resolution in [imports.js](src/jsyooptypecheck/imports.js).
- **Generics (Phase 7.1)**: generic decls (structs/funcs/traits with `typeParams`) are registered in per-module `genericStructTable`/`genericFuncTable`/generic-trait-table - **never** in the concrete `structTable`/`funcTable`, which only ever hold monomorphic types. `TypeParamType { name, originDecl }` placeholders appear inside generic bodies; `substituteTypeParams(type, sub, instantiator)` ([types.js:464](src/jsyooptypecheck/types.js#L464)) walks types replacing them. A **type-param scope** map is threaded through the `ctx` of `resolveTypeAnnotation()` so bare `T`s in a generic body resolve as `TypeParamType`s. The **instantiation registry** ([instantiate.js](src/jsyooptypecheck/instantiate.js)) is keyed by `(declId, argTypes)` and lazily monomorphizes structs/funcs/traits on demand - every concrete `StructType`/`FuncType` derived from a generic decl is cached, frozen, and reused. **Call-site inference** for generic functions runs inside `resolveExprType` on `CALL_EXPRESSION` in [checkExpr.js](src/jsyooptypecheck/checkExpr.js): walk param/arg types in tandem, unify each `TypeParamType` against concrete arg types, error on conflicts and on un-inferrable params (no turbofish - diagnostic is the workaround). Untyped int/float literals do **not** pin a type param; they default per existing rules only if every other arg constraining the param is also untyped.

### [src/jsyoopcodegen/](src/jsyoopcodegen/) - LLVM IR emission (~3,000 lines)
- Public entries:
  - `compileEntry(absPath)` at [codegen.js:2943](src/jsyoopcodegen/codegen.js#L2943) - full pipeline from entry file.
  - `codegenProgram(modules, _moduleEnv, programState)` at [codegen.js:1533](src/jsyoopcodegen/codegen.js#L1533) - multi-module IR from already-typechecked modules; `programState.registry` carries the instantiation registry from typecheck.
  - `codegen(ast)` at [codegen.js:216](src/jsyoopcodegen/codegen.js#L216) - single-module (legacy / tests).
- Single-pass AST → LLVM IR text. No intermediate IR, no optimization. Dispatchers: `emitStatement`, `emitExpr`, `emitCall`, `emitLvalue`. Temp + label counters reset per function.
- Emits to `/tmp/yooper_out.ll` and shells out to `clang` with link flags from [src/runtimeBuild.js](src/runtimeBuild.js).
- Multi-module symbol mangling: `<moduleId>__<symbolName>`. Internal to codegen; doesn't appear in user source.
- **`printf` lowering lives in two near-duplicate emitters that must stay in sync**: `emitPrintfCall` ([codegen.js](src/jsyoopcodegen/codegen.js)) and `emitPrintfCallInner` (the multi-module path). Contract: a call with an explicit format-string **literal** is C `printf` - the literal's `%` directives are authoritative and trailing value args fill them, so bare value args do **not** get an auto-appended specifier. A specifier is only synthesized for template-literal interpolations and for a bare value arg when no format literal is present (`printf(someString)` -> `%s`). Editing one emitter without the other reintroduces the doubled-directive bug (`printf("x=%d\n", x)` emitting format `"x=%d\n%d"`).
- **Generics (Phase 7.1)**: monomorphic struct/function definitions are emitted from the typechecker's instantiation registry, *not* by walking AST `TYPE_DECL`/`FUNCTION_DECL` nodes for generic decls. The registry walk in `codegenProgram` emits one LLVM struct per resolved `StructType` and one LLVM function per `FuncType` instance, mangled as `<moduleId>__<name>__<arg1>__<arg2>` (nested args flatten via the same `__` scheme). `structContainsTypeParam` ([codegen.js:1642](src/jsyoopcodegen/codegen.js#L1642)) is the gate that skips emitting "open" (still-parameterized) types. Generic function bodies are emitted by cloning the AST and pre-substituting type-param-bearing fields via `cloneAstWithSubstitution` ([codegen.js:1605](src/jsyoopcodegen/codegen.js#L1605)) - codegen never sees a `TypeParamType` directly.

### [src/jsyoopdriver/](src/jsyoopdriver/) - driver (~80 lines)

- [moduleId.js](src/jsyoopdriver/moduleId.js) - stable per-module id derivation (used for mangling).

## Cross-cutting invariants

The things that aren't obvious from reading any single file - read this section before editing across stages.

- **Codegen requires `node.resolvedType` on every node.** Codegen does zero type-checking. If you add an AST kind, the typechecker must set `.resolvedType` on it before codegen sees it, or codegen will crash or emit wrong IR.
- **Types are immutable (`Object.freeze`'d) - except `KindType` and `TypeParamType`.** `KindType` mutates during pass C.2 to fill in resolved clause details. `TypeParamType` mutates *once* during pass C of Phase 7.2 / 9.J to fill in its `bounds: TraitType[]` slot (one entry per `implements` clause; `<T implements Display>` → length 1, `<T implements (A, B)>` → length N); after that it's effectively immutable. `TraitType` is itself frozen, but its `methods: Map` and (Phase 9.J) `extendsTraits: TraitType[]` slots are mutable containers that pass C.1 populates — the outer object is sealed at construction, the maps/lists inside are not. Don't freeze KindType/TypeParamType; do treat every other type object as immutable.
- **Struct literals can't be typed standalone.** A bare `Foo { x: 1 }` returns an error from `resolveExprType`. Struct literals must be pinned to a target type via `checkInitializer` (assignment RHS, return value, call argument, etc.).
- **Binding type inference (the annotation is optional).** A `let`/`const` may omit its `: type` when it has an initializer (SPEC §4: "required without an initializer; optional when the initializer is unambiguous"). The parser leaves `typeAnnotation = null`; the type is inferred from the initializer in the typechecker. For locals this is in `checkLetOrConst` ([checkStatement.js](src/jsyooptypecheck/checkStatement.js)): `resolveExprType` the RHS, then `concretizeInferred` defaults `untypedInt` -> `int32` / `untypedFloat` -> `float64` (recursing into array elements, and re-pinning untyped array literals via `checkArrayLiteralWithElemType`) so the binding gets a concrete type identical to what an annotation would produce. For **module-level** bindings the inference is deferred to pass D.0 (`validateModuleInit`), because pass C.4 hasn't built the full per-module typeContext yet; the inferred type is published into `typeContext.moduleSymbols` (= `env.localSymbols`) so importers - which typecheck later in topological order - resolve the name correctly. Pass C.4 leaves `resolvedType = null` as the "infer later" sentinel (distinct from an `ErrorType` failure). Anything that can't be typed standalone (bare/orphan struct literals, empty array literals) yields a `cannot infer a type for "x"; add an explicit type annotation` error. Codegen is unchanged - it only ever sees a concrete `node.resolvedType`.
- **Two unrelated meanings of "kind" on a binding.** `binding.kind` = mutability (`"let"` / `"const"` / `"discard"`). `binding.kindType` = the Phase 6 user-defined kind declaration. Same word, orthogonal semantics.
- **Imported structs may be shells mid-pass.** Pass A registers struct types with `fields: null`; pass C fills them in. Don't assume a `StructType` from an imported module is fully populated before pass C completes.
- **Fallible `err` fields unobserved at scope exit are compile errors, not warnings.** Enforced in `popScope` via [fallible.js](src/jsyooptypecheck/fallible.js). Adding a new way to produce a fallible value means making sure `err` observation is tracked.
- **Error control flow differs by stage.** Lexer + parser throw and abort on first error. Typechecker accumulates into an `errors` array. Codegen assumes a clean AST and will crash on malformed input.
- **Source locations on every AST node are load-bearing.** Diagnostics rely on `node.sourceLoc` being set. Use `buildSourcedNode` (parser) or copy `sourceLoc` when synthesizing nodes elsewhere.
- **Generic decls live in a separate table from concrete ones.** The `structTable`/`funcTable`/`traitTable` only ever contain monomorphic types - generic decls go in `genericStructTable`/`genericFuncTable`/their trait equivalent and are instantiated lazily into the registry by `resolveTypeAnnotation` (for explicit type apps) and by call-site inference (for generic functions). Never put a `TypeParamType`-bearing type into a concrete table, and never reach across into the generic table when you mean to look up a concrete type.
- **Codegen never sees `TypeParamType`.** Generic struct/function bodies that reach codegen have been pre-substituted via `cloneAstWithSubstitution` so every `resolvedType` is concrete. If a `TypeParamType` ever appears in codegen, it's a typechecker bug - instantiation was missed at the use site.
- **Type aliases are transparent and live in their own table.** `type NodeId = usize;` parses to a `TYPE_DECL` with `targetType` (a type annotation) and NO `fields`; pass A registers it in the per-module `aliasTable` (name -> `{ annot, sourceLoc }`), never in `structTable`. Resolution is lazy and transparent: the `typeName` branch of both resolvers (`resolveTypeAnnotationInModule` in [typecheck.js](src/jsyooptypecheck/typecheck.js) and `resolveAnnotMulti` in [instantiate.js](src/jsyooptypecheck/instantiate.js)) consults the shared `lookupAlias` ([types.js](src/jsyooptypecheck/types.js)) and, on a hit, resolves the alias RHS *in the alias's home module* with a cycle-guard set - so the result IS the underlying type (no distinct identity, no special-casing for indexing/coercion, and **codegen never sees the alias name**). Cross-module aliases ride `importedNames` with `kind: "alias"`; namespaced (`ns.NodeId`) and chained aliases work. Pass C validates each alias RHS once (unknown target / cycle is a decl-site error) and stamps `d.resolvedAliasType` (NOT `d.resolvedType`, which would make codegen try to emit a struct). Generic aliases (`type Pair<T> = ...`) and composed RHS (`A & B`, `A | B`) are deferred - the deferred-feature diagnostic fires in pass A. The legacy single-module typecheck path does not support aliases (skips them).
- **Trait method calls are always trait-qualified (Phase 7.4).** Source form is `Trait.method(ref x, ...)`. Bare-form `method(ref x, ...)` is a typecheck error with a fix-it hint. The dotted form `x.method(...)` is also rejected (unchanged from Phase 5). Mangled symbols are `<structModuleId>__<StructName>__<TraitName>__<methodName>` via [mangleTraitMethod.js](src/jsyooptypecheck/mangleTraitMethod.js) - one LLVM `define` per (trait, method) pair, so cross-trait same-name impls work because each call site resolves to a distinct symbol. The typechecker tags every trait call with `calleeMethodOf` + `calleeTrait` + `calleeMethodName` + `calleeMangledName` (struct receiver) or `boundMethod` (TypeParamType receiver, rewritten post-substitution by codegen). **Phase 9.J: extends chain.** A trait declared `trait Child extends Parent { ... }` registers `Parent` in its `extendsTraits` slot during pass C.1. `validateImplBlock` flattens the chain into `StructType.implementsTraits` (every ancestor reachable from a user-declared trait is added, deduped by identity), so trait-method lookup against a struct never re-walks `extends`. The qualifying trait at a call site can be a descendant of the trait that *declares* the method (`BatchIterable.next(...)` where `next` is declared on `Iterable`); `resolveTraitQualifiedCall` walks the qualifying trait's extends chain to find the declaring trait and mangles using its name, so dispatch lines up with the single `Struct__<DeclaringTrait>__<method>` define. Multi-bound type params (`<T implements (A, B)>`) work the same way: bound-satisfaction and bound-method dispatch both `walkTraitExtends` across every bound.
- **`propagates<K>` is ADVISORY, not enforced (ownership redesign 2026-06-17).** See [plans/ownership-and-typestate-redesign.md](plans/ownership-and-typestate-redesign.md). The earlier "Phase 6.4 strict" model (a hard must-handle-or-hand-off contract) was reversed: the compiler is now **silent by default** about resource lifetimes. A type that declares `propagates<K>` is documenting "bindings of me own a resource" for readers and tooling; it does **not** force the user to do anything, and returning a propagating value never requires the function to declare `propagates<K>`. There are **no unsatisfied-obligation errors on the ownership side**. Avoiding double-free is the `dispose` implementer's responsibility (make `dispose` idempotent: free-then-null, guard on null). The two things that still have teeth:
  1. **Auto-cleanup (the one opt-in with codegen)**: declare the kind keyword on the binding (`disposable arr: T = ...`) and the compiler injects the cleanup call at scope end (unless a matching manual `Trait.method(ref arr)` already fired on every path). Same for the refcounted/builtin keywords (`pooled`/`joined`/`Task`) with their own auto-action (release / wait).
  2. **Manual discharge**: a plain `let`/`const` plus an explicit `Disposable.dispose(ref arr)`. Optional, never required.
  Implementation in [kindCheck.js](src/jsyooptypecheck/kindCheck.js): obligations are still computed per binding (`kindType`, `autoCleanup`, `satisfied`; `transferred`/`reported` are now vestigial), but `projectCleanups` only emits cleanup nodes for `autoCleanup` bindings and is otherwise **silent** - the old `reportUnsatisfied` error and the return-site `propagates<K>` transfer/enforcement were removed. `walkExpr` still flips `satisfied` for a matching `Trait.method(ref binding)` call so an already-hand-disposed `disposable` binding doesn't get a redundant injected cleanup. **Path coverage** (so a manual dispose on every reaching arm suppresses the injected cleanup): `IF_STATEMENT` and `SWITCH_STATEMENT` snapshot the sat state, walk each arm from that snapshot, and restore the intersection of reaching arms (diverged-via-`return` arms excluded via `walkDiverged`; SWITCH without a `default` also counts the fall-through path). `WHILE_STATEMENT`/`FOR_LOOP`/`FOR_IN_LOOP` discard inner sat changes (body may run zero times). **`SWITCH_STATEMENT` is now walked** specifically so a `disposable`-keyword binding inside a `case` arm still gets its auto-cleanup injected at the arm-block end (previously SWITCH was unwalked and those cleanups silently never fired). `BREAK`/`CONTINUE` remain no-ops in the walk. `runKindCheck` still runs on generic function decls (`effectiveImplementsTraits` reaches through `genericInstance.declId` into the registry for up-to-date traits). The marker/typestate kinds (next bullet) and `mustNotEscape`/`scoped` escape analysis are a SEPARATE, still-enforced concern - the relaxation only touched the ownership obligations.
- **Marker kinds are a static type-level check, and the kind decl is the authority for transitions.** A kind decl that names a polarity clause (`conferred;` or `restrictive;`) is a *marker* kind: no obligation, no `mustCall`, no codegen. A marker kind names itself in type position (`cleared string`, `tainted uint8[]`) - `parseTypeAnnotation` attaches `kindPrefixes: string[]` to the annotation. There are two enforcement points in [kindFlow.js](src/jsyooptypecheck/kindFlow.js):
  1. **Use-site bound check** at every slot (binding initializer, assignment, return, call argument): `slot.conferred subset-of value.conferred` (a conferred capability cannot be forged; sinks that name it REQUIRE it) and `value.restrictive subset-of slot.restrictive` (a restrictive hazard cannot be silently dropped; plain slots FORBID it). The return site is asymmetric - only the restrictive direction is enforced; the function's signature is the conferring authority (see point 2).
  2. **Decl-authority check** at every function decl: the kind decl pairs a required trait with a method name, and only an impl method of that trait may mediate the transition. A clearance kind declares `requires <Trait>;` plus `clearedBy <method>;` (restrictive) or `appliedBy <method>;` (conferred). For a function whose signature would strip a restrictive kind K (a parameter carries K, the return does not), the function MUST be a METHOD on a type whose `implements` list includes K's required trait, and its name MUST equal K.clearedBy. Same for the conferred direction. **Free functions are categorically rejected** - laundering requires opting in via a trait impl. This kills look-alike launderers (`evil(t: tainted X): X` returning a freshly-built `X` that secretly logs the input) and `fake_clear` minters: signature-shape matches don't authorize a transition; impl-of-the-named-trait does. The compiler still bakes in no "launder" verb - the user names the trait and its method; the kind decl just names them as the authority ("expressed sentiment"). The trait method itself has a plain signature (`function cleanse(ref self): T;` on a `Cleansable<T>`); the kind decl describes its semantic role rather than encoding it in the trait method's annotation, because trait methods require `ref self` as their first parameter and Yoop has no `Self` placeholder in return position - so generic traits (`Cleansable<T>` with `T` as the return type) are the idiomatic shape. Use sites: a trait-qualified call `Cleansable.cleanse(ref x)` is recognized by kindFlow via the typechecker-stamped `calleeMethodName` + `calleeTrait` on the CALL_EXPRESSION; the call's result carries every conferred kind whose `(appliedBy, requires.name)` pair matches. Arg sink-checks are skipped on trait calls (the kind decl is the contract).
  Because a binding's type is fixed at its declaration site - either from an explicit annotation or inferred once from its initializer (see "Binding type inference" below) - and assignments must conform, a binding's kind set is likewise fixed at declaration: there is no flow-sensitivity to track, no snapshot/merge, no per-binding kind state. The marker + obligation clauses are mutually exclusive on one kind, and `clearedBy` matches only `restrictive`, `appliedBy` only `conferred` (rejected in `populateKindFromClauses`). `parseKindClause` recognizes `conferred` / `restrictive` / `clearedBy` / `appliedBy` *contextually* inside a kind body so the words stay usable as ordinary identifiers everywhere else. Enforcement covers same-module direct calls (string callee), **imported by-name calls, and namespaced member calls (`ns.fn(...)`)** at parameter/return/binding sites: `kindFlow.runKindFlow` takes a `crossModuleCallee` resolver (built in `typecheck.js` pass D) that maps an imported/namespaced callee to its source decl plus that module's kind table, so a marker on a std-style signature is checked across the boundary instead of silently dropped (`exprMarkers`/`checkCallArgs` resolve via `callNode.calleeModuleId`/`calleeExportName` or `callee.namespaceLookup`; imported kinds share object identity, so the marker sets line up). Still follow-ups: **field-position sources** (a `tainted` struct field surfacing through `x.field` returns empty markers - field kinds are wired only to the ownership `propagates` path, and a `field` appliesTo site trips an ordering bug reporting `(none)`), and **trait-qualified calls to an imported *generic* trait** (`ImportedGenericTrait.method(...)` fails resolution with "undefined variable" before kindFlow even runs - a `resolveCall`/`lookupTraitByName` gap, not a kindFlow one). See [plans/clearance-kinds.md](plans/clearance-kinds.md).
- **Intrinsics enter scope via `extern "intrinsic"` blocks, not auto-injection.** The compiler-recognized intrinsics (`heap_alloc<T>`, `heap_free<T>`, `string_as_bytes`, `string_from_bytes_unchecked`, `array_slice<T>`, plus `wait_until<T>` / `cancel<T>`) used to be installed into every module's `genericFuncTable` at typecheck startup; they're now declared in [std/core/intrinsics.yoop](std/core/intrinsics.yoop) (and concurrency.yoop) inside `extern "intrinsic" from "compiler" { ... }` blocks. A user must `import * as intr from "std/core/intrinsics.yoop"` to call them as `intr.heap_alloc(...)`. The canonical decl objects (with stable `declId` like `$builtin__heap_alloc`) live in `makeBuiltinGenericFuncs()` ([typecheck.js](src/jsyooptypecheck/typecheck.js)) and the per-module `builtinIntrinsicNames: Set<string>` tracks which intrinsics are in scope; checkExpr.js's special-case branches for `wait_until` / `cancel` gate on this set so user code can shadow those names freely if it doesn't import concurrency.yoop. `printf` is the lone exception - it stays globally callable (the name doesn't collide with user identifiers and ~all examples use it). Codegen still dispatches intrinsics by `declId`, not by name; pass C of the typechecker skips type-annotation resolution for canonical generic intrinsics so the `T[]` in their extern-block signatures (documentation only) doesn't need a type-param scope.
- **Std value imports must be namespaced (`import * as ns from "std/..."`).** [imports.js](src/jsyooptypecheck/imports.js) rejects `import { f } from "std/..."` for any name that resolves to a value (function or const) with a fix-it pointing at the namespace form. Types / traits / kinds / enums / unions are exempt - their declaration-position usage (or capitalization) keeps them from competing with common identifiers. Imports from relative paths (e.g. within std/ itself, or user multi-file fixtures) are unaffected. To call a generic function through a namespace (`vec.vec_new<int32>()`, `intr.heap_alloc(8)`), the resolver consults `srcEnv.genericFuncTable` and routes to `resolveGenericCall` - see `resolveCall` and `checkInitializer` in [checkExpr.js](src/jsyooptypecheck/checkExpr.js), plus the `isNamespaceGenericCall` helper in [checkStatement.js](src/jsyooptypecheck/checkStatement.js) for the let-decl bidirectional-inference path. Codegen reads `node.genericInstantiation` on namespace-prefixed call sites so the emitted mangled name carries the type-arg suffix.
- **Enum and union are nominal types alongside struct, in their own tables (Phase 7.5).** `enumTable` / `unionTable` per module - siblings of `structTable`. Pass A registers shells; pass C fills variant payload field types (enums) and field types (unions). Variant ordinals are **stable 0-indexed integers in declaration order** and codegen emits them as `i32` tag values, so reordering a variant breaks ABI. Codegen reads `node.resolvedEnumType` + `node.resolvedVariant` on `VARIANT_CONSTRUCTOR` / `VARIANT_PATTERN` and `node.scrutineeType` on `SWITCH_STATEMENT` - these are stamped by the typechecker; if any are missing it's a typecheck bug. Untagged-union codegen emits a `{ [N x i8] }` byte buffer; field accesses bitcast through it, which assumes little-endian (the CI matrix is x86_64 + aarch64, both little-endian). Bare `EnumName.Variant` (no payload) parses as `FIELD_ACCESS` and is **promoted in-place** to `VARIANT_CONSTRUCTOR` by `resolveFieldAccess` when the LHS resolves to an enum - codegen never sees a `FIELD_ACCESS` whose object is an enum name.

## Design heuristics

- **Reach for a kind when the obligation moves with the value.** Yoop's kind system (`disposable`, `joined`, `pooled`, `Task`) exists for contracts that have to survive a return, a struct field, or a call across modules - places a comment that says "this MUST be called before X" or a parameter named `safe_*` / `unchecked_*` is doing a kind's job badly. Trigger sentence: "if you have one of these, it means X has happened to it." When you catch yourself writing that, stop and consider a kind. Cost / heuristics / in-tree opportunities (e.g. `validated` on safepath output, `authenticated` on a cleared Request) live in [plans/kinds-design.md](plans/kinds-design.md). One-off programs usually don't earn the cost; std-library APIs and cross-module contracts usually do.

## Test conventions

- Node's native test runner (`node --test`), style `describe` / `it` with `node:assert/strict`.
- Unit tests colocated as `<file>.test.js` next to source.
- [src/e2e.test.js](src/e2e.test.js) is the full lex → parse → typecheck → codegen → `clang` → run integration suite. Expensive but authoritative - when in doubt about whether a change works end-to-end, add a small fixture there.
